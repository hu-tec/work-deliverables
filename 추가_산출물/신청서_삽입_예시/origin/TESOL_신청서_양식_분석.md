# TESOL 신청서 양식 분석

분석 대상: `https://hu-tec.github.io/TESOL/apply`  
확인일: 2026-05-21

## 1. 전체 구조 요약

해당 페이지는 React 기반 SPA 안에 포함된 신청서 컴포넌트입니다. URL 경로에 따라 기본 신청 유형이 달라지고, 실제 신청서 화면은 중앙 정렬된 카드 형태의 폼으로 구성되어 있습니다.

쉽게 말하면, 신청서가 독립된 종이 양식처럼 존재하는 것이 아니라 홈페이지 안에 들어간 하나의 작은 프로그램처럼 동작합니다. 사용자가 어떤 버튼을 누르는지, 어떤 신청 유형을 선택하는지에 따라 다음에 보여줄 입력칸이 바뀝니다.

상단에는 신청 유형 탭이 있으며, 그 아래에 `신청서 Application Form` 제목과 3단계 진행 표시가 있습니다.

다만 실제 구현을 보면 사용자가 입력하는 화면은 2개 Step으로 나뉘어 있고, 세 번째 Step은 별도 입력 화면이 아니라 제출 완료를 의미하는 체크 아이콘 단계로 표현되어 있습니다.

현재 진행 구조는 다음과 같습니다.

| 단계 | 화면 의미 | 실제 입력 여부 | 비고 |
| --- | --- | --- | --- |
| Step 1 | 기본 정보 입력 | 있음 | 지원 구분, 성명, 연락처, 이메일, 생년월일, 국적 구분 |
| Step 2 | 상세 정보 입력 및 제출 | 있음 | 직업, 신청 경로, 신청 유형별 추가 정보, 자기소개, 약관 동의 |
| Step 3 | 완료 상태 | 별도 화면 없음 | 진행바에 체크 아이콘으로만 존재 |

비개발자 관점에서는 이 구조를 `신청서 첫 장 -> 신청서 둘째 장 -> 접수 완료 안내`로 이해하면 됩니다. 현재 페이지는 첫 장과 둘째 장은 실제로 있지만, 접수 완료 안내장은 아직 화면으로 따로 만들어져 있지 않은 상태입니다.

## 2. 신청 유형 탭 분석

폼 상단에는 신청 유형을 바꾸는 탭이 있습니다. 사용자가 탭을 누르면 신청 유형이 바뀌고 Step은 1단계로 돌아갑니다.

이 탭은 신청서의 목적을 먼저 고르는 장치입니다. 예를 들어 `레벨테스트`를 누르면 레벨테스트 신청서로, `1:1문의`를 누르면 문의 신청서로 같은 양식 안에서 성격이 바뀝니다.

| 신청 유형 | 영문 라벨 | 성격 |
| --- | --- | --- |
| 수업신청 | Class Apply | 오프라인 신청 정보 입력 필요 |
| 레벨테스트 | Level Test | 오프라인 신청 정보 입력 필요 |
| 설명회신청 | Seminar | 오프라인 신청 정보 입력 필요 |
| 테스트 TIP 신청 | Test TIP | 현재 구현상 문의 내용 입력형으로 처리됨 |
| 1:1문의 | 1:1 Inquiry | 문의 내용 입력 필요 |

URL별 기본 신청 유형 매핑은 다음과 같습니다.

| URL 경로 | 기본 신청 유형 |
| --- | --- |
| `/TESOL/apply` | 수업신청 |
| `/TESOL/apply/level-test` | 레벨테스트 |
| `/TESOL/apply/tip` | 테스트 TIP 신청 |
| `/TESOL/apply/corporate` | 1:1문의 |
| `/TESOL/apply/seminar` | 설명회신청 |
| `/TESOL/apply/orientation` | 수업신청 |

## 3. Step 1 분석: 기본 정보 입력

Step 1은 신청자의 기본 인적사항을 수집하는 단계입니다.

이 단계의 목적은 "누가 신청하는가"를 확인하는 것입니다. 이름, 연락처, 이메일처럼 담당자가 다시 연락하기 위해 반드시 필요한 정보가 들어갑니다.

### 3.1 입력 필드

| 필드 | 타입 | 필수 여부 | 선택지/형식 |
| --- | --- | --- | --- |
| 신청 유형 | 탭/버튼 | 필수 | 수업신청, 레벨테스트, 설명회신청, 테스트 TIP 신청, 1:1문의 |
| 지원 구분 | 단일 선택 | 필수 | TESOL, 프롬프트, AI 번역, AI윤리, ITT 번역교육 |
| 성명 | 텍스트 | 필수 | 자유 입력 |
| 연락처 | 텍스트 | 필수 | 숫자 입력 시 `010-1234-5678` 형식으로 자동 포맷 |
| 이메일 | 이메일 | 필수 | 이메일 정규식 검증 |
| 생년월일 | 날짜 | 필수 | 브라우저 기본 date input |
| 국적 구분 | 단일 선택 | 필수 | 내국인, 외국인, 재외국인 |

### 3.2 검증 로직

`다음 단계로` 버튼을 누르면 아래 순서로 검증합니다.

1. 신청 유형이 선택되어 있어야 합니다.
2. 지원 구분이 선택되어 있어야 합니다.
3. 성명이 비어 있으면 안 됩니다.
4. 연락처가 비어 있으면 안 됩니다.
5. 이메일은 비어 있거나 형식이 틀리면 안 됩니다.
6. 생년월일이 입력되어 있어야 합니다.
7. 국적 구분이 선택되어 있어야 합니다.

검증 실패 시 토스트 메시지로 오류를 보여주고 Step 2로 이동하지 않습니다.

### 3.3 UX 특징

- 필수 항목은 `*`로 표시됩니다.
- 국적 구분은 라디오 기반 단일 선택입니다.
- 지원 구분은 라디오처럼 단일 선택이지만, UI는 버튼형 칩에 가깝습니다.
- `취소` 버튼을 누르면 confirm 창을 띄운 뒤 전체 입력값을 초기화합니다.

## 4. Step 2 분석: 상세 정보 및 신청 내용

Step 2는 신청자 배경, 유입 경로, 신청 유형별 추가 정보를 수집하고 최종 제출하는 단계입니다.

이 단계의 목적은 "무엇을 신청하고, 어떤 일정이나 문의를 원하는가"를 확인하는 것입니다. 신청 유형에 따라 필요한 질문이 달라지므로, 모든 사람에게 같은 질문을 보여주지 않고 상황에 맞는 입력칸을 보여줍니다.

### 4.1 공통 입력 필드

| 필드 | 타입 | 필수 여부 | 선택지/형식 |
| --- | --- | --- | --- |
| 직업 | 단일 선택 | 필수 | 학생, 대학생, 직장인, 교사, 기타 |
| 신청을 알게 된 경로 | 복수 선택 | 필수 | 네이버 검색, 인스타그램, 유튜브, 지인 추천, 오프라인 안내, 기타 |
| 자기소개 | textarea | 필수 | 교육 참여 목적과 학습 목표 |
| 개인정보제공 약관동의 | 체크박스 | 필수 | 동의 여부 |

### 4.2 오프라인 신청 정보

다음 신청 유형은 오프라인 신청 정보 블록이 표시됩니다.

- 수업신청
- 레벨테스트
- 설명회신청

오프라인 신청 정보 필드는 다음과 같습니다.

| 필드 | 타입 | 필수 여부 | 선택지/형식 |
| --- | --- | --- | --- |
| 지역 | 복수 선택 | 필수 | 서울 강남, 부산 서면, 대구, 광주, 경기도, 충남, 강원도, 제주도 |
| 일자 | 날짜 입력 2개 | 필수 | 둘 중 1개 이상 입력 |
| 시간 | select 2개 | 필수 | 둘 중 1개 이상 선택 |

시간 선택지는 `09:00`부터 `18:00`까지 30분 단위입니다.

### 4.3 문의형 신청 정보

오프라인 신청 유형이 아닌 경우에는 오프라인 정보 대신 `문의 내용` textarea가 표시됩니다.

현재 코드 기준으로 `1:1문의`일 때만 문의 내용이 필수 검증됩니다. `테스트 TIP 신청`도 화면상 문의 내용 입력 블록이 표시되지만, 검증 로직상 문의 내용 필수 조건에는 포함되어 있지 않습니다.

### 4.4 Step 2 검증 로직

`제출하기` 버튼을 누르면 아래 순서로 검증합니다.

1. 직업이 선택되어 있어야 합니다.
2. 신청 경로가 1개 이상 선택되어야 합니다.
3. 자기소개가 입력되어 있어야 합니다.
4. 개인정보제공 약관에 동의해야 합니다.
5. 오프라인 신청 유형이면 지역을 1개 이상 선택해야 합니다.
6. 오프라인 신청 유형이면 일자를 1개 이상 입력해야 합니다.
7. 오프라인 신청 유형이면 시간을 1개 이상 선택해야 합니다.
8. `1:1문의`이면 문의 내용을 입력해야 합니다.

## 5. Step 3 분석: 완료 단계

진행 표시에는 세 번째 원형 단계가 존재하며 체크 아이콘으로 표시됩니다. 하지만 현재 구현에는 제출 성공 후 Step 3 화면으로 이동하는 상태 변경이 없습니다.

비유하면, 신청서를 제출한 뒤 접수증 화면이 따로 나오지 않고 상단 진행바에만 완료 표시 자리가 있는 상태입니다. 사용자는 토스트 알림으로 접수 여부를 알 수 있지만, 나중에 다시 확인할 수 있는 요약 화면은 없습니다.

현재 제출 성공 동작은 다음과 같습니다.

- 신청 데이터를 API로 POST 요청합니다.
- 성공 시 `신청서가 제출되었습니다. 담당자가 곧 연락드리겠습니다.` 토스트를 표시합니다.
- 실패 시 `제출 중 오류가 발생했습니다. 잠시 후 다시 시도해주세요.` 토스트를 표시합니다.
- 별도 완료 페이지, 완료 모달, Step 3 화면 전환은 없습니다.

따라서 3단계 구조를 명확히 만들려면 Step 3을 `제출 완료` 화면으로 실제 구현하는 것이 좋습니다.

권장 Step 3 구성:

| 영역 | 내용 |
| --- | --- |
| 완료 메시지 | 신청 접수 완료 안내 |
| 신청 요약 | 이름, 신청 유형, 지원 구분, 희망 일자/시간 |
| 후속 안내 | 담당자 연락 예정, 문의 채널 |
| 액션 | 새 신청서 작성, 홈으로 이동 |

## 6. 제출 데이터 구조 분석

제출 시 생성되는 데이터는 API에 맞춘 객체 형태로 변환됩니다.

API 엔드포인트:

```text
POST https://bmidcy9z17.execute-api.ap-northeast-2.amazonaws.com/api/tesol_expert_applications
```

주요 데이터 구조는 다음과 같습니다.

```json
{
  "applicant_id": "crypto.randomUUID()",
  "status": "pending",
  "applied_at": "YYYY-MM-DD HH:mm",
  "basic": {
    "name": "성명",
    "email": "이메일",
    "phone": "연락처",
    "birthDate": "생년월일",
    "course": "지원 구분",
    "job": "직업",
    "introduction": "자기소개 + 국적구분 + 신청경로 + 문의내용"
  },
  "application": {
    "available_languages": ["신청 유형"],
    "available_time": "희망 일자/시간 또는 미지정",
    "experience": "지역 목록 또는 온라인",
    "occupation": ["신청 경로"],
    "education": "국적 구분",
    "call_time": "신청 접수"
  },
  "extra": {
    "work_goals": [],
    "language_certs": [],
    "overseas_experience": "오프라인 신청 또는 온라인 신청",
    "mt_experience": "약관동의 완료 또는 약관동의 미완료"
  }
}
```

현재 데이터 구조는 백엔드 재사용 목적에 맞춰 일부 필드명이 실제 의미와 다르게 사용됩니다. 예를 들어 `available_languages`에는 언어가 아니라 신청 유형이 들어가고, `occupation`에는 직업이 아니라 신청 경로가 들어갑니다. 신규 구현이나 확장 시에는 프론트 전용 DTO와 API 전송 DTO를 분리하는 것이 좋습니다.

## 7. 다양한 페이지에 삽입하는 방식

신청서를 여러 페이지에 삽입하려면 현재 라우트 중심 구조보다 독립 위젯 구조가 적합합니다.

쉽게 말하면, 신청서를 특정 페이지에만 붙어 있는 고정 부품으로 만들지 말고, 여러 페이지에 옮겨 붙일 수 있는 공통 부품으로 만드는 것이 좋습니다. 그러면 레벨테스트 페이지, 설명회 페이지, 과정 상세 페이지마다 신청서를 새로 만들 필요가 없습니다.

### 7.1 권장 컴포넌트 인터페이스

```tsx
type ApplicationType =
  | "수업신청"
  | "레벨테스트"
  | "설명회신청"
  | "테스트 TIP 신청"
  | "1:1문의";

type ApplyFormProps = {
  defaultApplicationType?: ApplicationType;
  allowedApplicationTypes?: ApplicationType[];
  embedded?: boolean;
  theme?: ApplyFormTheme;
  onSubmit: (payload: ApplyFormPayload) => Promise<void> | void;
  onSuccess?: (payload: ApplyFormPayload) => void;
  onCancel?: () => void;
};
```

이렇게 분리하면 다음 방식으로 재사용할 수 있습니다.

```tsx
<ApplyForm
  defaultApplicationType="레벨테스트"
  allowedApplicationTypes={["레벨테스트"]}
  embedded
  theme={tesolTheme}
  onSubmit={submitApplication}
/>
```

### 7.2 페이지별 삽입 예시

| 삽입 위치 | 권장 기본값 | 탭 노출 방식 |
| --- | --- | --- |
| TESOL 과정 상세 | 수업신청 | 수업신청만 노출 또는 전체 노출 |
| 레벨테스트 안내 | 레벨테스트 | 레벨테스트만 노출 |
| 설명회 페이지 | 설명회신청 | 설명회신청만 노출 |
| 콘텐츠/이벤트 페이지 | 테스트 TIP 신청 | 테스트 TIP 신청만 노출 |
| 기업/단체 문의 | 1:1문의 | 1:1문의만 노출 |
| 공통 신청 페이지 | 수업신청 | 전체 신청 유형 노출 |

| 인라인 컴포넌트 | 페이지 본문 안에 직접 배치 | SEO/접근성/상태 공유에 유리 | 주변 레이아웃과 간격 충돌 가능 |
| 모달 | CTA 클릭 시 신청서 표시 | 상세 페이지 흐름을 끊지 않음 | 모바일에서 긴 폼 사용성 관리 필요 |
| 사이드 패널 | 데스크톱에서 우측 패널로 표시 | 상담/신청 전환에 유리 | 좁은 화면에서는 전체 화면 전환 필요 |
| iframe 위젯 | 외부 사이트에도 삽입 가능 | 배포와 격리가 쉬움 | 높이 자동 조절, 테마 전달, 추적 연동 필요 |
| Web Component | `<tesol-apply-form>` 형태로 삽입 | 프레임워크 독립적 | 초기 설계 비용이 큼 |

가장 현실적인 1차 구현은 `인라인 컴포넌트 + 모달 옵션`입니다. 외부 제휴 사이트까지 고려한다면 이후 iframe 또는 Web Component 형태를 별도 패키지로 분리하는 것이 좋습니다.

### 7.4 iframe 주소로 테마와 API를 바꾸는 방식

iframe 방식에서는 부모 페이지가 신청서 파일을 직접 고치지 않고, iframe 주소 뒤에 옵션을 붙여 신청서의 동작을 바꿀 수 있습니다.

예시는 다음과 같습니다.

```html
<iframe
  src="/apply-form-example.html?theme=green&type=레벨테스트&api=https%3A%2F%2Fexample.com%2Fapi%2Fapply"
  title="레벨테스트 신청서"
></iframe>
```

주소에 붙는 값의 의미는 다음과 같습니다.

| 파라미터 | 의미 | 예시 |
| --- | --- | --- |
| `theme` | 신청서 색상 테마 | `tesol`, `neutral`, `green`, `blue`, `teal`, `indigo`, `rose`, `amber`, `mono`, `soft`, `dark` |
| `type` | 처음 선택될 신청 유형 | `수업신청`, `레벨테스트`, `설명회신청`, `1:1문의` |
| `api` | 제출할 API 주소 | `https://example.com/api/apply` |
| `allowedTypes` | 노출할 신청 유형 제한 | `레벨테스트` 또는 `수업신청,설명회신청` |

비개발자 관점에서는 iframe 주소가 신청서의 설정표 역할을 한다고 보면 됩니다. 같은 신청서 파일을 쓰더라도 주소를 다르게 만들면 다른 색상, 다른 신청 유형, 다른 제출 API로 동작할 수 있습니다.

단, 실제 운영에서는 다음 사항을 확인해야 합니다.

1. API 서버가 iframe 도메인에서 오는 요청을 허용해야 합니다. 이것을 CORS 허용이라고 합니다.
2. `api` 주소를 URL로 직접 받으면 임의의 주소로 전송될 수 있으므로 운영 환경에서는 허용된 API 목록만 사용하도록 제한하는 것이 안전합니다.
3. iframe 높이는 내용에 따라 달라질 수 있으므로 `postMessage`로 높이를 부모 페이지에 알려 자동 조절하는 방식이 필요합니다.
4. 개인정보가 포함되므로 iframe 주소와 API 요청은 반드시 HTTPS를 사용해야 합니다.

## 8. 테마 변경을 고려한 설계

현재 폼은 Tailwind 클래스와 고정 색상값이 섞여 있습니다. 대표 색상은 `#8B1A2B`이며, 카드 배경은 흰색, 보조 배경은 `#fafafa`, 경계선은 `black/10` 계열입니다.

테마 변경 가능성을 높이려면 색상과 라운드, 폰트, 밀도 값을 CSS 변수로 분리해야 합니다.

여기서 테마란 신청서의 기능은 그대로 두고 겉모습만 바꾸는 설정을 뜻합니다. 예를 들어 TESOL 페이지에서는 버건디 색을 쓰고, AI 번역 페이지에서는 초록색이나 파란색을 쓰고, 어두운 배경의 랜딩 페이지에서는 다크 테마를 쓰는 방식입니다.

### 8.1 CSS Variable 쉬운 설명

CSS Variable은 웹페이지 디자인에서 쓰는 `공통 색상표` 또는 `공통 스타일 값`이라고 이해하면 됩니다.

예를 들어 신청서 곳곳에 직접 `#8B1A2B`라는 색상값을 반복해서 적으면, 나중에 브랜드 색을 바꿀 때 모든 파일을 찾아 수정해야 합니다. 반대로 `--apply-primary`라는 이름표를 만들어두고 버튼, 진행바, 선택된 탭이 모두 그 이름표를 바라보게 하면 색상 변경이 쉬워집니다.

즉 아래 두 방식의 차이입니다.

```css
/* 직접 색상값을 쓰는 방식 */
.button {
  background: #8b1a2b;
}

.step-dot {
  background: #8b1a2b;
}
```

```css
/* CSS Variable을 쓰는 방식 */
.apply-form {
  --apply-primary: #8b1a2b;
}

.button {
  background: var(--apply-primary);
}

.step-dot {
  background: var(--apply-primary);
}
```

두 번째 방식에서는 `--apply-primary` 값만 바꾸면 버튼, 진행바, 선택된 탭의 색상이 한 번에 바뀝니다.

### 8.2 CSS Variable을 쓰면 좋은 점

| 장점 | 설명 |
| --- | --- |
| 테마 변경이 쉬움 | 색상값 하나만 바꿔도 여러 UI가 같이 변경됩니다. |
| 여러 페이지에 삽입하기 좋음 | 같은 신청서를 페이지 분위기에 맞게 다르게 꾸밀 수 있습니다. |
| 유지보수가 쉬움 | 버튼 색, 테두리 색, 배경색을 파일 곳곳에서 찾지 않아도 됩니다. |
| 브랜드 확장에 유리 | TESOL, AI 번역, 프롬프트 과정별 색상만 다르게 적용할 수 있습니다. |
| 개발자와 디자이너 협업이 쉬움 | `주요 색상`, `배경색`, `테두리`처럼 의미 있는 이름으로 관리할 수 있습니다. |

### 8.3 권장 테마 토큰

```css
.apply-form {
  --apply-primary: #8b1a2b;
  --apply-primary-hover: #781625;
  --apply-primary-soft: rgb(139 26 43 / 0.06);
  --apply-bg: #ffffff;
  --apply-surface: #fafafa;
  --apply-text: #111111;
  --apply-muted: rgb(0 0 0 / 0.55);
  --apply-border: rgb(0 0 0 / 0.10);
  --apply-radius: 12px;
  --apply-control-radius: 6px;
  --apply-font-family: Pretendard, system-ui, sans-serif;
}
```

각 값의 의미는 다음과 같습니다.

| CSS Variable | 쉬운 의미 | 사용 위치 예시 |
| --- | --- | --- |
| `--apply-primary` | 대표 색상 | 주요 버튼, 선택된 탭, 진행 단계 |
| `--apply-primary-hover` | 버튼에 마우스를 올렸을 때 색상 | 제출 버튼 hover |
| `--apply-primary-soft` | 대표 색상의 아주 연한 배경 | 선택된 항목 배경, focus 효과 |
| `--apply-bg` | 신청서 카드 배경색 | 전체 폼 배경 |
| `--apply-surface` | 보조 영역 배경색 | 오프라인 신청 정보 박스 |
| `--apply-text` | 기본 글자색 | 제목, 입력값 |
| `--apply-muted` | 덜 강조되는 글자색 | 라벨, 보조 설명 |
| `--apply-border` | 테두리 색 | 카드, 입력칸, 구분선 |
| `--apply-radius` | 큰 박스의 둥근 정도 | 신청서 카드, 탭 |
| `--apply-control-radius` | 입력칸/버튼의 둥근 정도 | input, select, button |
| `--apply-font-family` | 글꼴 | 신청서 전체 |

### 8.4 테마 프리셋 예시

| 테마 값 | 주요 사용처 | 색상 방향 |
| --- | --- | --- |
| `tesol` | 현재 TESOL 페이지 | 버건디 포인트, 흰 배경 |
| `neutral` | 제휴/공통 페이지 | 검정/회색 중심, 브랜드 색 최소화 |
| `green` | 교육/상담형 페이지 | 녹색 포인트 |
| `blue` | 신뢰감 있는 안내 페이지 | 파란색 포인트 |
| `teal` | AI/기술 교육 페이지 | 청록색 포인트 |
| `indigo` | 전문 과정/심화 과정 | 인디고 포인트 |
| `rose` | 이벤트/프로모션 페이지 | 로즈 포인트 |
| `amber` | 설명회/오프라인 안내 | 앰버 포인트 |
| `mono` | 미니멀한 페이지 | 흑백 중심 |
| `soft` | 밝고 조용한 랜딩 페이지 | 부드러운 뉴트럴 톤 |
| `dark` | 어두운 랜딩 페이지 | 어두운 배경, 밝은 텍스트 |

### 8.5 테마 적용 예시

```tsx
const tesolTheme = {
  primary: "#8B1A2B",
  bg: "#ffffff",
  surface: "#fafafa",
  text: "#111111",
  border: "rgb(0 0 0 / 0.10)",
  radius: "12px"
};
```

```tsx
<ApplyForm theme={tesolTheme} />
```

또는 DOM 속성 기반으로 적용할 수 있습니다.

```html
<section data-apply-theme="tesol">
  <div id="apply-form-root"></div>
</section>
```

```css
[data-apply-theme="tesol"] {
  --apply-primary: #8b1a2b;
}

[data-apply-theme="neutral"] {
  --apply-primary: #111111;
}
```

비개발자 관점에서는 `data-apply-theme="tesol"`이 "TESOL 옷을 입혀라"라는 표시이고, `data-apply-theme="neutral"`은 "무채색 옷을 입혀라"라는 표시라고 보면 됩니다. 신청서의 질문과 제출 기능은 그대로이고, 색상과 분위기만 바뀝니다.

## 9. 개선 권장 사항

1. Step 3을 실제 완료 화면으로 구현합니다.
2. `테스트 TIP 신청`의 문의 내용 필수 여부를 정책적으로 결정합니다.
3. 프론트 입력 데이터와 API 전송 데이터를 분리합니다.
4. 신청 유형별 필수 필드를 설정 객체로 분리합니다.
5. 고정 색상값을 CSS 변수 또는 theme prop으로 치환합니다.
6. 페이지별 삽입을 위해 `ApplyForm`을 라우트와 분리된 독립 컴포넌트로 유지합니다.
7. 모달/인라인/iframe 삽입을 고려해 `embedded`, `variant`, `allowedApplicationTypes` 옵션을 둡니다.
8. 제출 성공 후 완료 화면, 재작성 버튼, 신청 요약을 제공합니다.

신청 유형별 정책은 다음처럼 설정 객체로 분리하는 것이 좋습니다.

```ts
const applicationTypeConfig = {
  "수업신청": {
    mode: "offline",
    requiresInquiry: false
  },
  "레벨테스트": {
    mode: "offline",
    requiresInquiry: false
  },

    mode: "offline",
    requiresInquiry: false
  },
  "테스트 TIP 신청": {

  },

    mode: "inquiry",
    requiresInquiry: true
  }
};
```

이 구조로 바꾸면 페이지 삽입 위치가 늘어나도 폼 내부 로직을 복사하지 않고 설정만 바꿔 재사용할 수 있습니다.

## 11. 결론

현재 신청서는 시각적으로 3단계처럼 보이지만 실제 사용 흐름은 `기본 정보 입력 -> 상세 정보 및 제출 -> 토스트 알림`입니다. 여러 페이지에 삽입하고 테마를 바꿀 수 있는 재사용형 폼으로 발전시키려면 Step 3 완료 화면을 명시적으로 추가하고, 신청 유형별 필드 정책과 테마 토큰을 컴포넌트 외부 설정으로 분리하는 것이 핵심입니다.

우선순위는 다음과 같습니다.

1. Step 3 완료 화면 추가
2. 신청 유형별 필드/검증 설정 분리
3. `ApplyFormProps` 기반 독립 컴포넌트화
4. CSS 변수 기반 테마 토큰 적용
5. 인라인/모달/iframe 삽입 방식 지원
