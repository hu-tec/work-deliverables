# figma_pdf 기반 자료와 design_resource 기반 자료 비교 분석

## 1) 결론 요약

`figma_pdf` 기반 MD는 전체 범위와 대략적인 사이트맵을 파악하는 데는 유용하지만, 실제 개발 구현에 필요한 화면 단위의 필드, 버튼, 모달, 상태 전이, 라우트 매핑을 충분히 제공하지 못한다. 반면 `design_resource`는 프레임별 JPG가 역할/업무별 폴더로 분리되어 있고, 별도 docs까지 구성되어 있어 개발자가 구현 단위로 바로 해석하기 쉽다.

따라서 이 프로젝트의 개발 기준은 `figma_pdf -> 개괄 분석`보다 `design_resource -> 화면 인벤토리 -> 플로우 MD -> 구현 매핑 -> 코드 구현` 순서가 더 적합하다.

## 3) figma_pdf 기반 MD가 부실해진 이유

### 3.1 PDF 추출물은 구현 단위가 아니라 시각 자료 묶음에 가깝다

PDF 파일은 화면을 보관하는 데는 적합하지만, 개발자가 필요한 구조화 정보가 자동으로 남지 않는다. 특히 다음 정보가 빠지기 쉽다.

- 버튼 클릭 후 도착 화면
- 확인/취소 모달의 분기
- 저장 후 상태값 변경
- 필수 입력값과 검증 규칙
- 테이블 컬럼별 데이터 의미
- 권한별 접근 가능 화면
- API 또는 localStorage로 관리해야 하는 상태

실제 `figma_pdf_2025_사이트맵_기능정의.md`에도 PDF 내부 텍스트 추출 도구가 없어 PDF는 파일명과 확인 가능한 메타 정보 중심으로 해석했다는 주의가 들어 있다. 이 조건에서는 화면의 의도와 흐름을 추정할 수는 있어도, 구현 명세로 확정하기 어렵다.

### 3.2 파일명 중심 분석은 화면 흐름을 평면화한다

`figma_pdf` 기반 문서는 `로그인`, `회원관리`, `시험관리`, `결제` 같은 메뉴와 기능명을 정리하는 데는 성공한다. 하지만 화면 간 연결 관계는 파일명만으로 충분히 복원되지 않는다.

예를 들어 `시험접수 변경`, `시험접수 취소`, `저장팝업`, `제출확인`, `회원탈퇴 환불` 같은 파일은 각각 존재해도, 실제 구현에서는 다음이 더 중요하다.

- 어떤 화면에서 어떤 버튼으로 진입하는가
- 취소 시 이전 상태가 유지되는가
- 확인 시 목록 상태가 어떻게 바뀌는가
- 토스트가 뜨는가, 모달이 닫히는가
- 실패 상태와 빈 상태가 있는가

PDF 기반 MD는 이 흐름을 충분히 계층화하지 못한다.

### 3.3 2024/2025/바이브의 역할이 섞이면 구현 우선순위가 흐려진다

`2024_figma_사이트맵_기능정의.md`는 AITP 시험 플랫폼의 전체 업무 흐름을 잘 정리한다. 수험생, 출제자, 채점자, 관리자 역할과 큰 메뉴 구조를 파악하는 데 적합하다.

반면 `figma_pdf_2025_사이트맵_기능정의.md`는 2025 자료를 전체 시험 플랫폼 IA라기보다 기존 시험 플랫폼 위에 적용할 UX/UI 참고 화면과 일부 관리자/전문가 화면으로 해석한다. 이처럼 2024와 2025의 성격이 다르기 때문에, PDF 기반으로만 통합하면 다음 문제가 생긴다.

- 2024의 핵심 시험 운영 흐름과 2025의 UX 참고 화면이 같은 구현 우선순위처럼 보인다.
- 확정 기능과 참고 UI가 구분되지 않는다.
- 개발자는 어떤 화면을 먼저 구현해야 하는지, 어떤 화면은 디자인 패턴만 차용해야 하는지 판단하기 어렵다.

### 3.4 기존 구현 문서에서도 같은 한계가 확인된다

`../hutechc_app_v2/docs/02-why-implementation-keeps-missing-flows.md`는 PDF 문서가 전체 범위 파악에는 좋지만, 구현에 필요한 필드/버튼/상태/도착 화면을 충분히 제공하지 못한다고 정리한다.

또한 이 문서는 누락이 반복된 원인을 `design_resource`의 화면 플로우를 먼저 구현 명세로 변환하지 않고, 파일명과 큰 범위만 보고 바로 구현한 것으로 본다. 이 판단은 이번 비교 분석과 일치한다.

## 4) design_resource 기반 도출의 장점

### 4.1 화면 단위가 개발 단위와 더 잘 맞는다

`design_resource`는 JPG 화면이 역할/업무 폴더에 배치되어 있다. 예를 들어 2024에는 로그인/로그아웃, 회원가입/전문가가입, 응시생, 출제, 채점, 관리자, 결제, 마이페이지가 분리되어 있다.

이 구조는 개발자가 다음 단위로 바로 나눌 수 있다.

- 라우트
- 페이지 컴포넌트
- 테이블/폼/모달 컴포넌트
- 권한별 메뉴
- mock 데이터
- 테스트 케이스

PDF처럼 한 파일 안에 화면이 묶여 있거나 파일명만 남는 구조보다 구현 분해가 쉽다.

### 4.2 최신 UI와 기본 업무 흐름을 함께 흡수할 수 있다

`docs/README.md`의 작성 기준은 명확하다.

- 2024: 큰 업무 흐름과 기본 사용자 여정
- 2025: 최신 UI/UX 기준
- 바이브: 고도화, 운영 확장, AI/관리 기능 강화

이 기준을 쓰면 2024, 2025, 바이브를 서로 경쟁하는 버전이 아니라 하나의 제품 명세로 통합할 수 있다. 개발 관점에서는 2024로 IA와 역할별 업무를 잡고, 2025로 공통 에디터/팝업/토스트/전문가 프로필 같은 최신 UI를 보강하며, 바이브로 AI/운영 고도화 기능을 추가하는 방식이 된다.

### 4.3 별도 docs가 구현 명세 역할을 한다

`../hutechc_design_resource/docs`에는 통합 제품 문서와 기능별 문서가 이미 정리되어 있다.

통합 제품 문서:

- 사용자 역할과 권한
- 정보 구조
- 사용자 플로우
- 화면 명세
- 기능 요구사항
- 데이터 모델/API 후보
- 구현 계획
- 오픈 이슈

기능별 문서:

- 인증/온보딩
- 시험 응시
- 응시생 마이페이지
- 출제
- 채점
- 관리자 코어
- 결제/정산
- 전문가 프로필
- 공통 UI
- AI/운영 고도화

이 구조는 개발자가 “무엇을 만들지”뿐 아니라 “어디에 붙일지”를 판단하는 데 직접 도움을 준다.

## 5) figma_pdf vs design_resource 구현 가능성 비교

| 비교 항목 | figma_pdf 기반 | design_resource 기반 |
|---|---|---|
| 전체 범위 파악 | 가능. 사이트맵과 큰 메뉴 정리에 유리 | 가능. 폴더와 docs를 함께 보면 더 명확 |
| 화면 단위 식별 | 파일명 중심이라 한계 있음 | JPG가 프레임별로 분리되어 유리 |
| 사용자 플로우 | 추정 필요 | docs와 폴더 구조로 보강 가능 |
| 필드/버튼/모달 파악 | PDF 품질과 추출 상태에 의존 | 화면 이미지에서 직접 확인 가능 |
| 상태 전이 정의 | 별도 작성 필요 | 기능별 MD로 확장하기 쉬움 |
| 구현 우선순위 | 2024/2025/바이브 성격이 섞일 수 있음 | 2024=기본 흐름, 2025=최신 UI, 바이브=고도화로 분리 가능 |
| 개발자 전달력 | 개괄 설명용 | 구현 명세용 |
| 누락 위험 | 높음 | 상대적으로 낮음 |
| 유지보수성 | PDF 재해석이 필요 | docs 업데이트로 관리 가능 |

## 6) design_resource docs를 별도 MD로 만들었을 때 개발 용이성

`design_resource`의 docs처럼 별도 MD를 만들면 다음 효과가 있다.

### 6.1 구현 전에 화면 누락을 발견할 수 있다

화면 인벤토리를 만들면 `회원가입`, `본인인증`, `시험접수 변경/취소`, `출제 저장팝업`, `채점 피드백`, `관리자 대량관리`처럼 빠지기 쉬운 화면을 구현 전에 드러낼 수 있다.

### 6.2 개발자와 기획자의 언어가 맞춰진다

JPG 화면만 있으면 개발자는 컴포넌트와 라우트 관점으로 해석하고, 기획자는 업무 흐름 관점으로 해석한다. MD 문서는 다음 항목을 공통 언어로 만든다.

- 화면 목적
- 진입 경로
- 사용자 권한
- 주요 UI 영역
- 입력 필드
- 버튼/액션
- 클릭 후 도착 화면
- 모달/토스트
- 상태 전이
- 예외/빈 상태

### 6.3 기존 앱에 흡수하기 쉬워진다

`../hutechc_app_v2/docs/01-v2-cause-analysis.md`는 v2 작업에서 기존 `hutechc_app`을 기준 소스이자 베이스라인으로 삼아야 한다고 정리한다. design_resource docs가 있으면 각 화면을 기존 구조의 `PortalShell`, 역할별 라우트, 관리자 하위 메뉴, mock 데이터에 매핑할 수 있다.

즉 새 단일 mock 앱을 만드는 대신, 기존 포털 구조에 누락 기능을 흡수할 수 있다.

### 6.4 테스트 케이스로 바로 연결된다

화면별 MD에 액션과 상태 전이가 있으면 테스트 항목을 바로 만들 수 있다.

예시:

- 회원가입 필수값 누락 시 검증 메시지 표시
- 시험접수 취소 확인 모달에서 취소 시 상태 유지
- 확인 시 접수 상태가 `취소됨`으로 변경
- 채점 확정 후 완료 토스트 표시
- 관리자 파일 업로드 후 업로드 이력 추가

이 수준의 테스트는 PDF 파일명만으로는 만들기 어렵다.

## 7) 권장 진행 방식

앞으로 이 프로젝트는 다음 순서로 진행하는 것이 적절하다.

1. `figma_pdf` 문서는 전체 범위와 역사적 맥락 파악용으로 사용한다.
2. 실제 구현 기준은 `../hutechc_design_resource`와 `../hutechc_design_resource/docs`로 둔다.
3. 구현 전 `화면 인벤토리`, `화면 플로우 명세`, `구현 매핑` MD를 먼저 만든다.
4. 기존 앱을 새로 대체하지 않고 `../hutechc_app` 또는 `../hutechc_app_v2`의 역할별 구조에 흡수한다.
5. 각 기능은 버튼/모달/토스트/상태 전이까지 정의한 뒤 구현한다.
6. 테스트와 빌드로 누락 여부를 확인한다.

## 8) 최종 판단

`figma_pdf` 기반 산출물은 기획 자료를 빠르게 훑어 전체 메뉴를 파악하는 데 적합하다. 하지만 실제 개발 구현을 안정적으로 진행하기에는 정보가 너무 평면적이다.

`design_resource` 기반 산출물은 프레임 단위 화면과 docs가 함께 있어, 구현 단위로 분해하고 기존 앱에 연결하기 쉽다. 특히 별도 MD 문서를 만들면 화면 누락, 플로우 누락, 상태 전이 누락을 줄일 수 있다.

따라서 최종 산출물과 개발 진행의 기준은 `design_resource + docs` 방식으로 두는 것이 맞다. `figma_pdf`는 보조 근거로 유지하되, 구현 명세의 기준으로 삼기에는 부족하다.
