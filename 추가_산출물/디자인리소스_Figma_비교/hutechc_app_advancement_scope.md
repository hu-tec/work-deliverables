# hutechc_app 기준 기능 고도화 범위 분석

## 1) 결론 요약

현재 `../hutechc_app`은 시험 포털의 기본 화면 구조, 역할별 진입점, 수험자 주요 플로우, 일부 전문가/채점자/관리자 화면을 가진 프론트엔드 프로토타입이다. `design_resource + docs`를 기준으로 보강하면 단순 클론을 넘어 **업무 흐름이 연결된 고충실도 프론트엔드 프로토타입**까지 고도화할 수 있다.

다만 현재 앱에는 백엔드, 인증/권한, 실제 결제, 파일 업로드 처리, 운영 데이터 저장소가 없다. 따라서 현재 기준에서 바로 도달 가능한 최대치는 **실제 API 없이 mock/localStorage 기반으로 동작하는 구현 검증용 포털**이다. 운영 가능한 제품 수준까지 가려면 API, DB, 인증, 결제, 파일 저장, 감사 로그가 별도 구축되어야 한다.

## 2) 현재 hutechc_app 구현 범위

근거 위치: `../hutechc_app`

### 기술 구조

- Next.js App Router 기반
- `app/[locale]` 다국어 라우팅 구조
- 한국어/영어 사전: `lib/i18n.ts`
- Tailwind CSS, 로컬 UI primitive, lucide-react 아이콘 사용
- Vitest + Testing Library 테스트 구성

주요 파일:

- `components/exam-portal.tsx`: 첫 화면 포털 대시보드
- `components/portal-shell.tsx`: 역할별 페이지 셸, 라우트 매핑, 워크스페이스 렌더링
- `components/exam-data.ts`: 포털 메트릭, 접수 목록, 준비 상태 mock 데이터
- `components/grading-workbench.tsx`: 전문가/채점자 채점 워크벤치
- `components/inquiry-workspace.tsx`: 1:1 문의 목록/작성/상세, localStorage 저장
- `components/take-question-tabs.tsx`: 시험 응시 문항 탭
- `components/theme-settings.tsx`: 테마 설정, localStorage 저장
- `components/exam-portal.test.tsx`: 핵심 화면/상호작용 테스트

- 프로필 테마: 테마 선택 후 localStorage 저장
- 관리자 화면: 운영 그리드 형태의 mock 화면 제공

현재 앱은 실제 업무 데이터 처리보다, 포털 화면 구조와 UX 흐름을 검증하는 데 초점이 맞춰져 있다.

## 3) design_resource와 결합했을 때 고도화 가능 범위

`../hutechc_design_resource`와 `../hutechc_design_resource/docs`를 기준으로 보면, 현재 앱은 다음 방향으로 확장 가능하다.

### 3.1 수험자 플로우 고도화

현재:

- 시험접수 7단계가 정적 상태로 표시됨
- 시험응시 화면과 결과/자격증/결제 화면이 mock 데이터로 구성됨
- 1:1 문의는 localStorage 기반으로 일부 실제 동작함

고도화 가능:

- 회원가입, 간편가입, 본인인증, 아이디 찾기, 비밀번호 재설정 추가
- 시험 접수 변경/취소/환불/연기 플로우 연결
- 응시 전 환경 점검, 시험 시작/제출/종료/다음 차시 상태 전이 구현
- 번역형, 음성/영상형, 웹툰형, 프롬프트형, 단답형 시험 UI 분리
- 결과 조회, 이의신청, 자격증 발급/재발급/출력 상태 관리
- 접수/결제/응시/결과/자격증 상태를 하나의 mock 상태 모델로 연결

도달 수준:

- 백엔드 없이도 수험자가 처음 가입해서 시험을 보고 결과를 확인하는 전체 시나리오를 클릭 가능한 프로토타입으로 만들 수 있다.

### 3.2 출제자/전문가 플로우 고도화

현재:

- 전문가 대시보드, 제출목록, 번역채점, 정산, 프로필 화면이 있음
- 채점 워크벤치는 후보자 선택과 기준표 확인 중심

고도화 가능:

- 출제관리 목록/상세 추가
- 번역형/프롬프트형/단답형 출제 화면 분리
- 출제 저장, 임시저장, 제출, 확인 팝업, 반려 후 수정 플로우 구현
- 전문가 프로필 상세 입력: 학력, 경력, 저서/역서, 해외거주 경험, 첨부파일 UI 구현
- 전문가 정산 내역, 작업 상태, 마감 임박, 반려/승인 상태 연결
- AI 또는 전문가 검수 요청 플로우를 시험/채점/정산과 연결

도달 수준:

- 출제자가 문제를 작성하고 제출하며, 채점/정산까지 확인하는 업무형 워크스페이스 수준까지 고도화 가능하다.

### 3.3 채점자 플로우 고도화

현재:

- 채점 워크벤치에서 응시자 선택, 원문/답안/기준표, 점수 입력 UI 제공
- 저장/확정은 실제 상태 변경 없이 UI 수준에 가깝다

고도화 가능:

- 채점 대상 목록, 개별 채점, 다음 채점 이동
- 번역형/프롬프트형/단답형 채점 상세 분리
- 평가 기준표 팝업, 피드백 작성, 보류/재검토/확정 상태 전이
- AI 점수와 휴먼 점수 비교, 차이 큰 항목 표시
- 저장/확정/재검토 요청 모달과 토스트 연결
- 채점 완료 후 결과 조회와 관리자 채점관리 상태까지 연결

도달 수준:

- 실제 채점 업무 흐름을 프론트엔드에서 검증할 수 있는 워크벤치형 프로토타입까지 가능하다.

### 3.4 관리자/운영 플로우 고도화

현재:

- 운영자 홈, 채점관리, 문의관리, 결제내역 정도로 제한됨
- 관리자 하위 메뉴가 실제 design_resource 범위보다 좁다

고도화 가능:

- 회원관리, 관리자/그룹관리, 전문가관리, 신규 응시자 관리
- 시험관리, 시험 신규 등록, 일정/지역/응시조건 관리
- 출제관리, 문제관리, 채점관리, 자격증관리
- 결제관리, 환불, 정산관리, 요금제, 장바구니
- 고객지원, 게시판/FAQ, 1:1 문의관리
- 사이트관리, 알림창관리, 메인배너 관리
- 카테고리/코드 관리
- 양식관리, 템플릿 양식 관리자
- 파일 업로드형 대량관리, 엑셀 다운로드/업로드 mock
- 통계 대시보드, 운영 리스크 큐

도달 수준:

- 현재 3개 하위 관리자 화면을 `design_resource` 기준의 운영 콘솔 구조로 확장할 수 있다.
- 백엔드 없이도 검색, 필터, 상태 pill, 확인 모달, 토스트, localStorage 이력 수준의 운영 시뮬레이션은 가능하다.

### 3.5 공통 UI/시스템 고도화

현재:

- 공통 셸, 헤더, 사이드바, 패널, 배지, 버튼, 입력 UI가 있음
- 알림 드롭다운과 테마 설정이 일부 동작함

고도화 가능:

- 공통 모달, 토스트, 파일 업로드, 에디터, 탭, 테이블, 필터바, 페이지네이션 정리
- 2025 공통 에디터 패턴을 시험 응시, 출제, 채점, 양식관리로 확장
- 알림 설정과 실제 알림 목록/상태 연결
- 상태별 색상, 빈 상태, 오류 상태, 로딩 상태 표준화
- 반응형 관리자 테이블 패턴 정리
- 디자인 토큰과 화면 밀도 기준 정리

도달 수준:

- 일관된 디자인 시스템을 가진 업무형 포털로 정리 가능하다.

## 4) 고도화 단계 정의

| 단계 | 수준 | 설명 | 현재 hutechc_app 위치 |
|---|---|---|---|
| 0단계 | 정적 클론 | 주요 화면을 정적으로 재현 | 일부 완료 |
| 1단계 | 라우트형 프로토타입 | 역할별 화면과 주요 라우트 제공 | 상당 부분 완료 |
| 2단계 | 상태 기반 프로토타입 | 입력, 검색, 필터, localStorage, 모달/토스트 상태 전이 | 일부 완료 |
| 3단계 | 업무 시나리오 프로토타입 | 가입-접수-결제-응시-채점-결과-자격증-정산 연결 | design_resource 기반 보강 필요 |
| 4단계 | 운영 준비형 프론트엔드 | API 연동 전제의 화면/상태/권한/오류/테스트 체계 완성 | 추가 설계 필요 |
| 5단계 | 실제 운영 제품 | 백엔드, DB, 인증, 결제, 파일 저장, 감사 로그, 운영 배포 | 현재 범위 밖 |

현재 앱은 1단계와 2단계 사이에 있다. `design_resource + docs`를 적용하면 3단계까지는 충분히 도달 가능하고, API 명세까지 확정하면 4단계 프론트엔드까지 갈 수 있다. 5단계는 별도 백엔드 구축이 필요하다.

## 6) 고도화 우선순위

### 1순위: 구현 누락이 큰 화면을 문서화

먼저 `design_resource` 기준으로 화면 인벤토리와 플로우 명세를 만든다.

- 인증/회원가입/전문가 신청
- 시험접수 변경/취소
- 시험응시 시작/제출/종료
- 출제 저장/제출/반려
- 채점 피드백/확정
- 관리자 회원/시험/출제/양식/템플릿/대량관리

### 2순위: 기존 hutechc_app 구조에 라우트 흡수

새 앱을 만들지 않고 `PortalShell`의 라우트와 역할별 사이드바에 추가한다.

- 수험자: `/ko/signup`, `/ko/auth/verify`, `/ko/take/session`, `/ko/withdraw`
- 전문가: `/ko/expert/authoring`, `/ko/expert/templates`
- 채점자: `/ko/grader/workbench`, `/ko/grader/history`
- 관리자: `/ko/admin/members`, `/ko/admin/exams`, `/ko/admin/forms`, `/ko/admin/templates`, `/ko/admin/bulk`

### 3순위: mock 상태 모델 연결

각 화면을 독립 mock이 아니라 하나의 상태 흐름으로 묶는다.

- 접수 상태
- 결제 상태
- 응시 상태
- 채점 상태
- 결과 상태
- 자격증 상태
- 문의 상태
- 관리자 처리 상태

### 4순위: 모달/토스트/파일/에디터 공통화

`design_resource`의 2025 팝업, 토스트, 공통 에디터, 파일 업로드 화면을 공통 컴포넌트로 만든다.

### 5순위: API 전환 준비

mock 데이터와 localStorage를 API 후보 명세와 맞춘다.

- 화면별 필요한 entity 정의
- list/detail/update action 분리
- 실패/빈 상태/권한 오류 처리
- 테스트 케이스 작성

## 7) 최종 판단

현재 `hutechc_app`은 좋은 베이스라인이다. 이미 업무형 포털 톤, 역할별 진입, 수험자 핵심 화면, 문의 localStorage, 채점 워크벤치, 테스트 구조가 있다. 따라서 고도화는 새로 만드는 방식보다 **기존 `hutechc_app`을 기준으로 design_resource의 화면과 docs를 흡수하는 방식**이 맞다.

현실적인 도달점은 다음과 같다.

- 현재 자료만으로 가능: 고충실도 프론트엔드 프로토타입, mock/localStorage 기반 업무 시나리오
- API 명세까지 만들면 가능: 운영 준비형 프론트엔드
- 백엔드/DB/인증/결제/파일 저장까지 붙이면 가능: 실제 운영 제품

따라서 이번 분석 기준에서 기능 고도화 목표는 우선 **3단계 업무 시나리오 프로토타입**으로 두고, 이후 API 명세를 확정해 **4단계 운영 준비형 프론트엔드**까지 확장하는 것이 적절하다.
