# 업무산출물 사이트 기반 AI 작업 요청 가이드

대상 저장소: `C:\Users\itban\Desktop\핵심_산출물\work-deliverables`

공개 화면: https://hu-tec.github.io/work-deliverables/

이 문서는 AI에게 **현황 분석, 기능 검토, 오류 수정, 새 화면 제작**을 요청할 때 쓰는 복사형 프롬프트 모음이다. 개발 용어를 몰라도 `[대괄호]` 안만 채워서 사용할 수 있다. 공개 사이트는 화면 확인용이고, 실제 수정 범위와 데이터의 기준은 작업 시점의 로컬 Git 소스에서 확인한다. 공개 화면과 로컬 소스가 다르면 차이를 보고하게 한다.

현재 저장소의 메인 `index.html`에는 HTML·Markdown·레퍼런스 링크·DB 정제 자료·프로젝트 소스/내부 도구 탭이 있다. HTML과 Markdown은 검색과 보기 전환, 원문/미리보기, 일부 다운로드 기능을 제공한다. 요청할 때는 반드시 **어느 탭, 어느 항목, 어느 동작**인지 적는다.

## 1. 먼저 정할 세 가지

| 항목 | 선택 예시 | 왜 필요한가 |
|---|---|---|
| 작업 모드 | `읽기만`, `검토·제안만`, `범위 내 구현` | “분석해줘”를 AI가 수정 허가로 오해하지 않게 한다. |
| 변경 범위 | `index.html의 HTML 검색 동작만` | 관련 없는 데이터·화면 변경을 막는다. |
| 완료 기준 | `검색 후 표시 개수와 실제 행 수가 일치` | 결과를 눈으로 확인할 수 있게 한다. |

**‘데이터는 건드리지 마’의 정확한 뜻**도 적는다. 이 저장소에서 데이터는 원본 HTML/Markdown, `DATA`의 목록·제목·경로·분류·날짜·`sourceDocs`, `file-dates.js`, `db-files.js`, `reference-links.js`, ZIP과 다운로드 연결까지 포함할 수 있다. 기능 수정 중 필요한 코드 변경까지 막는 표현이 되지 않도록, 보호할 값과 허용할 코드 변경을 구분한다.

## 2. 모든 요청에 붙이는 공통 블록

아래 블록을 복사한 뒤 `작업 모드`와 `수정 허용 파일`을 채운다. 분석만 원하면 `수정 허용 파일: 없음`으로 둔다.

```text
작업 위치: C:\Users\itban\Desktop\핵심_산출물\work-deliverables
참고 화면: https://hu-tec.github.io/work-deliverables/
작업 모드: [읽기만 / 검토·제안만 / 범위 내 구현]
대상: [탭, 화면, 파일, 기능 또는 자료명]
수정 허용 파일: [정확한 경로 또는 없음]

작업 전 확인:
1. 저장소의 AGENTS.md와 대상 파일, 관련 기준 문서를 읽어줘.
2. 현재 Git 변경사항을 확인하고 기존 사용자 작업은 보존해줘.
3. 공개 화면에서 보이는 내용과 로컬 소스가 다르면 어느 쪽을 근거로 판단했는지 밝혀줘.

보호 기준:
- 내가 지정하지 않은 원본 파일, 자료 제목·본문, 분류, 개수, 날짜, 경로, 다운로드 링크, ZIP, 연결된 Markdown 관계는 변경하지 마.
- 기존 색상, 글꼴, 간격, 컴포넌트, 화면 구조를 임의로 바꾸지 마. 필요한 디자인 변경이 있으면 먼저 변경 위치와 이유를 제안해줘.
- 확인되지 않은 내용은 추측해서 채우지 말고 ‘확인 필요’로 표시해줘.
- 커밋·푸시·배포는 이 요청에 명시했을 때만 해줘.

완료 보고:
- 확인한 근거 파일과 경로
- 변경한 파일과 변경 이유 또는 ‘변경 없음’
- 실제로 검증한 항목과 결과
- 확인하지 못한 사항 및 남은 결정 사항
```

이 블록은 기본 안전장치다. **자료 추가, 분류 변경, 디자인 변경을 실제로 원할 때는 그 항목을 “변경 허용”에 명시**한다. 막연한 전면 금지와 변경 요청을 동시에 쓰면 작업이 멈추거나 해석이 흔들린다.

## 3. 요청 문장을 바꾸는 방법

| 막연한 요청 | 더 신뢰할 수 있는 요청 |
|---|---|
| “사이트 분석해줘.” | “HTML 탭의 검색·보기 전환·미리보기·다운로드 흐름을 읽기 전용으로 점검하고, 정상 동작/재현 가능한 오류/확인 불가를 나눠 표로 보고해줘.” |
| “문제 있으면 고쳐줘.” | “검색 결과 개수 불일치만 수정해줘. `index.html`의 검색·개수 계산 관련 코드만 변경하고, 자료 배열과 CSS는 유지해줘.” |
| “예쁘게 바꿔줘.” | “`디자인시스템/docs/재사용_디자인_프롬프트/00_문서목록.md`에서 해당 화면 기준을 찾고, 현재 색상·타이포그래피·간격을 유지한 상태에서 버튼 정렬 문제만 수정해줘.” |
| “새 페이지 만들어줘.” | “대상 사용자·필수 내용·참고 화면·새 파일 경로·디자인 기준·완료 기준을 아래처럼 지정할게. 이 범위로 새 페이지를 만들어줘.” |
| “데이터 정리해줘.” | “실제 자료 수와 현재 분류를 표로 제안만 해줘. 제목·경로·날짜·원문·다운로드 연결은 수정하지 마.” |

## 4. 복사해서 쓰는 상황별 프롬프트

### A. 현재 사이트의 기능을 읽기만 하며 점검

```text
작업 위치: C:\Users\itban\Desktop\핵심_산출물\work-deliverables
작업 모드: 읽기만. 파일을 수정하거나 생성하지 마.

메인 index.html의 [HTML / Markdown / 레퍼런스 링크 / DB 정제 자료 / 프로젝트 소스·내부 도구] 탭 중 [대상 탭]을 일반 사용자 관점에서 점검해줘.

점검 범위: [예: 검색 → 항목 선택 → 미리보기 → 원문 열기 → 다운로드]
각 단계마다 화면에 기대되는 결과와 소스에서 확인한 실제 동작을 비교해줘.
문제는 재현 순서, 기대 결과, 실제 결과, 근거 파일·코드 위치, 사용자 영향으로 정리해줘.
직접 실행하지 못한 항목은 ‘미검증’이라고 표시하고 정상이라고 단정하지 마.
마지막에는 우선순위와 수정 제안을 제시하되 구현하지 마.
```

### B. 신규 기능을 만들기 전에 타당성 검토

```text
작업 모드: 검토·제안만. 현재 파일은 수정하지 마.
저장소: C:\Users\itban\Desktop\핵심_산출물\work-deliverables

검토할 기능: [예: HTML 탭에서 파일 형식별 필터 추가]
사용자 목적: [예: 필요한 산출물을 더 빨리 찾기]
대상 화면: [예: 메인 index.html의 HTML 탭]

현재 코드와 관련 문서를 확인하고 아래 순서로 답해줘.
1. 현재 동작과 관련 파일
2. 구현 방법 1~2개와 각각 영향받는 파일
3. 자료 수·제목·경로·다운로드·미리보기 연결에 미치는 영향
4. 기존 디자인을 유지하는 화면 배치안
5. 완료 기준과 검증 방법
6. 사용자 결정이 꼭 필요한 사항만 질문

확인되지 않은 기능이나 데이터를 있는 것처럼 가정하지 마.
```

### C. 기능 오류를 제한된 범위에서 바로 수정

```text
작업 모드: 범위 내 구현
저장소: C:\Users\itban\Desktop\핵심_산출물\work-deliverables
증상: [예: HTML 검색 결과를 지운 뒤 표시 개수가 돌아오지 않음]
재현: [1. HTML 탭 열기 → 2. 검색어 입력 → 3. 검색어 삭제]
기대 결과: [예: 전체 목록과 실제 행 수가 다시 표시]
수정 허용 파일: [예: index.html]

먼저 원인을 관련 코드로 확인하고, 이 오류를 해결하는 최소 범위만 수정해줘.
자료 제목·본문·분류·날짜·경로·다운로드 대상과 기존 CSS는 바꾸지 마.
수정 후에는 재현 절차를 다시 확인하고, 검색어 있음/없음, 표/카드 보기 전환, 미리보기와 다운로드에 회귀 문제가 없는지 점검해줘.
결과에는 원인, 변경 위치, 검증 결과, 미검증 항목을 적어줘.
```

### D. 기존 디자인을 따라 새 페이지 만들기

```text
작업 모드: 범위 내 구현
저장소: C:\Users\itban\Desktop\핵심_산출물\work-deliverables
새 산출물 폴더: [예: 신규_신청안내/]
목적과 대상 사용자: [누가, 어떤 일을 하려는지]
필수 콘텐츠: [확정된 문구·표·링크·이미지 경로]
필수 기능: [예: 검색, 신청 버튼, FAQ 열기]

디자인 기준:
- 먼저 디자인시스템/docs/재사용_디자인_프롬프트/00_문서목록.md를 읽고 이 화면에 맞는 기준 문서를 골라 적용해줘.
- 기준 화면: [정확한 기존 HTML 경로]
- 유지할 요소: [헤더, 색상, 글꼴, 버튼, 간격, 테이블/카드 방식]
- 새 색상 체계, 새로운 폰트, 의미 없는 장식 이미지, 기존과 다른 메뉴 구조를 임의로 만들지 마.

자료 기준:
- 위 ‘필수 콘텐츠’만 사실로 사용해줘. 없는 가격·일정·수치·연락처는 만들지 말고 표시가 필요하면 ‘확인 필요’로 남겨줘.
- 기존 파일은 수정하지 말고 새 폴더 안에 필요한 파일을 만들어줘.

완료 기준:
- 데스크톱과 모바일에서 내용이 잘리거나 겹치지 않는다.
- 지정한 기능이 실제로 동작한다.
- 기준 화면과 다른 부분은 이유를 설명한다.
- 생성 파일 목록과 검증 결과를 보고한다.
```

새 화면이 **관리자용**이면 `디자인시스템/docs/재사용_디자인_프롬프트/관리자/`의 문서를, **일반 사용자용**이면 `.../사용자/`의 문서를 우선 지정한다. 관리자용 고밀도 테이블 규칙을 사용자 안내 페이지에 그대로 적용하지 않도록 용도를 적는다.

### D-1. 기존 랜딩페이지의 원본 데이터를 대조하면서 새 랜딩페이지 만들기

이 경우에는 “원본을 참고해줘”보다 **원본으로 인정할 파일, 옮길 범위, 의도적으로 바꿀 내용, 전후 대조표**를 지정해야 한다. 랜딩페이지의 문구가 HTML에만 있는 것은 아니다. 예를 들어 이 저장소의 시험 랜딩페이지는 `index.html`에 직접 쓴 내용과 `data.js`·`site.js`로 표시하는 내용을 함께 확인해야 한다. 협회 랜딩페이지는 `content.js`의 데이터도 확인해야 한다. 실제 화면에 렌더링된 값까지 검수해야 누락을 찾을 수 있다.

아래는 **기존 메인 랜딩페이지의 정보는 유지하고 디자인·배치만 바꾸는 경우**에 바로 쓸 수 있는 예시다.

```text
작업 모드: 범위 내 구현
저장소: C:\Users\itban\Desktop\핵심_산출물\work-deliverables
원본 기준: 랜딩페이지/랜딩페이지3종/시험/index.html
원본과 함께 확인할 파일: 같은 폴더의 data.js, site.js, styles.css, assets/ 및 메인에 실제로 연결된 파일
새 산출물: [새 폴더명]/index.html 및 그 폴더에 필요한 파일
목표: 원본 메인 랜딩페이지의 정보와 동작을 유지하면서 [원하는 새 디자인/배치]로 제작
콘텐츠 범위: 원본 메인 화면에 실제로 표시되는 내용. 연결된 다른 페이지의 본문은 이번 범위에서 제외

1. 제작 전에 원본 화면의 메뉴, 섹션, 제목, 본문, 수치·날짜·가격, 표/카드 항목, 버튼 문구와 링크, 이미지와 대체 텍스트, 푸터를 목록으로 만들어줘.
   HTML에 직접 적힌 값과 JS에서 생성되는 값을 모두 포함하고, 각 항목의 출처 파일과 코드 위치를 적어줘.
2. 원본 데이터는 임의로 요약·교정·재작성하지 마. 오탈자나 서로 모순되는 값도 조용히 고치지 말고 원문대로 옮긴 뒤 ‘원본 확인 필요’로 따로 보고해줘.
3. 섹션 순서와 메뉴 구조는 유지해줘. 변경이 꼭 필요한 디자인 요소는 [허용한 범위] 안에서만 바꿔줘.
4. 원본 파일은 수정하지 말고 새 폴더에 결과물을 만들어줘. 경로가 바뀌어 상대 링크나 이미지 경로를 고쳐야 한다면 원본 경로 → 새 경로를 기록하고, 실제로 열리는지 확인해줘.
5. 완성 후 원본 항목과 새 페이지의 실제 표시 항목을 1:1로 대조해줘. 누락, 추가, 문구 변경, 수치 변경, 링크 오류를 구분해줘. 공백·줄바꿈 차이만 있는 경우와 의미가 바뀐 경우를 구별해줘.
6. 메뉴·CTA 클릭, 이미지 로딩, 화면 폭 [예: 1440px, 390px]에서의 표시를 확인해줘. 실행하지 못한 검사는 ‘미검증’으로 남겨줘.

완료 보고 형식:
| 원본 항목 | 원본 위치 | 새 페이지 위치 | 판정(일치/의도적 변경/누락/확인 필요) | 근거 |
원본과 새 페이지의 총 메뉴 수, 섹션 수, 반복 항목 수를 함께 적어줘.
불일치가 있으면 수정한 뒤 다시 대조하고, 해결되지 않은 불일치를 남긴 채 ‘완료’라고 하지 마.
커밋·푸시는 하지 마.
```

**원본 데이터를 일부만 가져오는 새 목적의 랜딩페이지**라면 “전부 옮겨라” 대신 포함·제외·변경 대상을 먼저 지정한다. 다음 블록을 위 프롬프트의 `콘텐츠 범위` 자리에 넣는다.

```text
콘텐츠 범위:
- 반드시 가져올 것: [원본의 메뉴/섹션/항목명]
- 이번 페이지에서 제외할 것: [원본의 메뉴/섹션/항목명과 제외 이유]
- 변경을 허용할 값: [원본 값 → 새 값, 변경 근거]
- 새로 추가할 내용: [확정된 문구와 제공 파일]
- 나머지 원본 항목은 변경하지 말 것

검증 시 원본의 각 항목을 ‘사용/의도적 제외/승인된 변경’ 중 하나로 매핑해줘.
목록에 없는 항목을 임의로 버리거나, 새 가격·일정·실적·연락처를 만들어 넣지 마.
```

원본이 **외부 운영 사이트 URL**이면 그 URL만 적지 말고, 확인할 페이지 목록과 저장된 원본 파일 또는 캡처 시점을 함께 지정한다. 운영 사이트와 저장소 데이터가 다르면 어느 쪽이 최종 기준인지 명시한다. 접근할 수 없는 페이지는 옮긴 것으로 간주하지 않게 한다.

### D-2. 현재 디자인시스템으로 새 결과물을 만들고 관련 기능 문서까지 연결하기

새 화면·서비스·도구 등 무엇을 만들든 **대상의 이름, 목적, 사용자 행동**을 적어야 AI가 관련 문서를 골라낼 수 있다. 디자인 문서는 모양과 상호작용의 기준이고, 기능정의 문서는 무엇을 해야 하는지의 근거다. 같은 이름의 오래된 시안이나 예시 데이터가 섞여 있을 수 있으므로 문서의 역할과 적용 이유를 먼저 확인한다.

**먼저 관련 문서만 찾아보고 싶을 때:**

```text
작업 모드: 검토·제안만. 파일을 수정하지 마.
저장소: C:\Users\itban\Desktop\핵심_산출물\work-deliverables
만들 대상: [새 화면·서비스·도구의 이름]
목적: [예: 운영자가 시험 접수 현황을 검색하고 상세 상태를 확인하는 화면]
사용자와 주요 행동: [누가 / 무엇을 조회·입력·저장하는지]

먼저 AGENTS.md와 디자인시스템/docs/재사용_디자인_프롬프트/00_문서목록.md를 읽어줘.
그다음 이 대상의 목적에 맞는 디자인 기준, 기능정의, 데이터 원천, 유사한 기존 화면을 저장소에서 찾아줘.
파일명만 보고 판단하지 말고 관련 문서의 실제 본문과 적용 범위를 확인해줘.

각 자료를 ‘디자인 기준 / 기능 요구사항 / 데이터 원천 / 구현 참고 / 과거 시안’으로 분류하고,
경로, 관련 절·항목, dd에 적용할 내용, 선택 이유를 표로 제시해줘.
중복·구버전·상충 문서는 근거를 붙여 표시하고, 어떤 기준을 채택할지 제안해줘.
저장소에 근거가 없는 기능은 ‘문서 없음’으로 표시하고 새 요구사항처럼 만들어내지 마.
마지막에 만들 대상의 기능 목록, 화면 구성 초안, 결정이 필요한 사항만 정리해줘.
```

**문서 탐색부터 제작·검증까지 맡길 때:**

```text
작업 모드: 범위 내 구현
저장소: C:\Users\itban\Desktop\핵심_산출물\work-deliverables
만들 대상: [새 화면·서비스·도구의 이름]
목적: [예: 시험 접수 관리 화면]
대상 사용자와 주요 행동: [예: 운영자가 접수자를 검색하고 결제·응시 상태를 확인]
새 파일 위치: [예: 새 폴더명/index.html]
반드시 구현할 기능: [확정된 기능 2~5개]
사용할 실제 데이터: [제공한 파일 경로 또는 ‘없음’]
원본에서 반드시 보존할 값: [해당 시 제목·수치·경로·상태값 등]

1. 문서 탐색
   - AGENTS.md와 디자인시스템/docs/재사용_디자인_프롬프트/00_문서목록.md를 먼저 읽어줘.
   - 만들 대상이 사용자 화면인지 관리자 화면인지 목적을 기준으로 판단하고, 해당 폴더의 기준 문서와 필요한 공통 컴포넌트 문서만 골라줘.
   - 저장소에서 만들 대상과 관련된 기능정의·사이트맵·데이터 사전·기존 화면을 실제 내용으로 확인해줘.
   - 예를 들어 시험 기능이라면 추가_산출물/시험홈페이지_통합_구현/source/기능상세정의.md와 관련 사이트맵 문서를 후보로 확인하되, 관련 없는 항목까지 자동 적용하지 마.

2. 근거 연결
   - 아래 표를 먼저 작성해줘.
     | 기능/화면 요소 | 근거 문서·절 | 적용할 디자인 기준 | 데이터 출처 | 구현 위치 | 검증 방법 |
   - 문서마다 ‘확정 기준/참고/과거 시안’을 구분해줘. 충돌하는 내용은 임의로 합치지 말고 차이와 권장안을 설명해줘.
   - 근거 없는 가격·일정·상태값·버튼 동작을 만들지 마. 필수 결정이 비어 있으면 그 결정만 질문해줘.

3. 구현
   - 연결표에서 근거가 확인되고 내가 확정한 기능만 구현해줘.
   - 현재 디자인시스템의 토큰·컴포넌트·레이아웃을 우선 재사용하고, 임의의 새 색상·폰트·메뉴 체계를 만들지 마.
   - 기존 원본 파일과 실제 데이터를 수정하지 말고 지정한 새 파일에 작성해줘. 재사용 때문에 원본 변경이 필요하면 위치와 이유를 먼저 알려줘.

4. 검증과 보고
   - 연결표의 각 행마다 실제 구현 여부와 확인 결과를 표시해줘.
   - 검색·입력·저장·상세보기 등 요청된 기능은 사용자 조작 순서로 확인해줘.
   - 원본 데이터의 항목 수와 값, 링크, 날짜가 새 화면에 맞게 옮겨졌는지 대조해줘.
   - 검증하지 못한 항목은 ‘미검증’, 문서가 없는 기능은 ‘근거 없음’으로 남겨줘.
   - 변경 파일과 디자인 기준에서 벗어난 부분을 보고해줘. 커밋·푸시는 하지 마.
```

만들 대상의 이름만 있고 목적이 정해지지 않았다면 먼저 첫 번째 프롬프트로 관련 자료와 기능 범위를 확인한다. 목적·주요 행동·새 파일 위치가 정해졌으면 두 번째 프롬프트로 바로 제작할 수 있다.

### E. 기존 화면에 기능을 추가하되 자료와 디자인을 보존

```text
작업 모드: 범위 내 구현
저장소: C:\Users\itban\Desktop\핵심_산출물\work-deliverables
대상: index.html의 [정확한 탭/영역]
추가할 기능: [한 문장]
사용자 시나리오: [시작 → 조작 → 기대 결과]
수정 허용 파일: [정확한 파일 목록]

현재 자료 목록의 항목 수, 제목, 순서, 날짜, 파일 경로, 다운로드 연결, sourceDocs 연결을 작업 전 기록해줘.
기존 검색·표/카드 전환·미리보기와 겹치는 동작은 기존 패턴을 재사용해줘.
CSS 변경이 꼭 필요하면 대상 영역에 한정하고, 색상·글꼴·전체 레이아웃은 유지해줘.
작업 후 보호 대상의 전후 차이를 확인하고, 달라진 항목이 있으면 요청 범위인지 설명해줘.
완료 기준: [측정 가능한 동작 2~4개]
```

### F. 자료 분류만 검토하거나, 승인된 분류만 적용

**1단계: 검토용**

```text
작업 모드: 읽기만. 자료를 옮기거나 수정하지 마.
대상: [index.html 또는 analyze.html의 자료 목록]

현재 대분류·중분류·개별 자료와 실제 개수를 먼저 세어줘.
중복·누락·분류가 모호한 항목을 원래 제목과 경로를 인용해 표로 보여줘.
새 분류안을 제안하되 모든 기존 항목이 새 분류 어디에 들어가는지 매핑표를 만들어줘.
총 항목 수가 보존되는지 확인하고, 판단이 어려운 항목은 임의로 분류하지 말고 별도 표시해줘.
아직 파일은 변경하지 마.
```

**2단계: 사용자가 분류안을 확정한 후 적용용**

```text
작업 모드: 범위 내 구현
대상 파일: [정확한 경로]
적용할 확정 분류안: [대분류/중분류별 기존 항목 목록 또는 앞서 확정한 매핑표]
변경 허용: 위 항목의 분류 표시와 이를 위해 필요한 목록 코드만
변경 금지: 항목 추가·삭제, 제목·본문·날짜·파일/다운로드 경로·ZIP·sourceDocs 변경

작업 전후 전체 항목 수와 각 분류의 실제 행 수를 비교해줘.
검색 결과 수, 표/카드 보기, 미리보기, 다운로드가 계속 맞는지 점검해줘.
매핑표에 없는 항목은 이동하지 말고 보고해줘.
```

표2·카드형2의 정확한 동작을 유지해야 하는 작업이면 [`표2_카드형2_대중소분류_작업요청_가이드.md`](../표2_카드형2_대중소분류_작업요청_가이드.md)를 대상 파일과 함께 지정한다. 그 문서는 해당 자료 카탈로그용 기준이므로 다른 관리자 화면 전체에 일괄 적용하지 않는다.

### G. 디자인 개선안을 보고 싶지만 실제 변경은 보류

```text
목업이나 코드 변경은 하지 마.
```

### I. 개발 완료 후 별도 검수

```text

Git 변경사항과 실제 파일을 비교해줘.
```

## 5. 상세 분석과 개발을 한 번에 맡길 때

작업이 명확하고 수정 범위가 이미 정해졌다면 아래 방식이 효율적이다. 실제 자료 수정이나 새 디자인 선택처럼 사용자의 판단이 필요한 결정만 중간에 묻고, 나머지 구현과 검증은 이어서 진행하게 한다.

```text
작업 모드: 범위 내 구현
저장소: C:\Users\itban\Desktop\핵심_산출물\work-deliverables
목표: [사용자가 하려는 일]
대상 화면/파일: [정확한 경로]
현상과 기대 결과: [재현 순서, 현재 결과, 원하는 결과]
수정 허용 파일·데이터·디자인: [각각 구체적으로]
보호할 항목: [각각 구체적으로]
완료 기준: [검증 가능한 항목 2~5개]

순서:
1. 현재 동작, 관련 파일, 원인을 근거와 함께 요약해줘.
2. 변경 범위와 보호 항목을 짧게 확인해줘.
3. 지정된 범위 안에서 구현하고 실제 동작을 검증해줘.
4. 변경 파일, 전후 차이, 검증 결과, 남은 이슈를 보고해줘.

자료의 의미를 바꾸거나 새 디자인 방향을 선택해야 하면 해당 선택지만 질문해줘.
그 외에는 이 요청의 범위 안에서 진행해줘.
```

## 6. 신뢰성을 높이는 완료 기준 예시

“잘 만들어줘” 대신 아래에서 해당하는 것을 골라 붙인다.

- **목록/분류:** 작업 전후 총 항목 수가 같고, 화면에 표시된 분류별 수와 실제 행 수가 같다.
- **검색:** 검색어 입력·삭제·결과 없음에서 목록과 개수가 일치한다.
- **보기 전환:** HTML의 표/카드 보기에서 같은 자료가 같은 제목·경로·순서로 나타난다.
- **미리보기:** 항목을 선택하면 의도한 원본이 열리고, 관련 Markdown 연결이 있으면 올바른 문서를 보여준다.
- **다운로드:** 버튼이 존재하는 실제 파일을 가리키며, 선택 다운로드는 선택한 항목만 처리한다.
- **새 화면:** 제공한 문구와 자료만 노출하며, 지정한 데스크톱·모바일 너비에서 텍스트가 겹치거나 잘리지 않는다.
- **기존 디자인 유지:** 기준 화면과 비교해 요청하지 않은 색상·글꼴·간격·헤더·컴포넌트 변화가 없다.
- **검증 보고:** 테스트하거나 직접 열어본 항목과 못 본 항목을 구별한다.

## 7. 자료를 함께 전달하는 법

파일을 많이 나열하는 것보다 **역할**을 지정하는 편이 정확하다.

```text
기준 화면: [이 HTML의 레이아웃·디자인을 따른다]
디자인 기준: [이 Markdown의 규칙을 적용한다]
콘텐츠 원천: [이 파일의 문구와 값만 사용한다]
기능 참고: [이 JS의 동작만 참고한다]
수정 대상: [이 파일만 수정한다]
보호 대상: [이 파일의 원문·날짜·경로는 유지한다]
```

예를 들어 관리자 테이블을 만들 때는 `디자인시스템/table_design/관리자패널_전체회원.html`을 **기준 화면**, `디자인시스템/docs/재사용_디자인_프롬프트/관리자/02_BO_테이블레이아웃_기준.md`를 **디자인 기준**이라고 지정한다. 참고 HTML의 예시 데이터는 실제 데이터로 취급하지 않는다. 자세한 자료 전달 예시는 [`다른페이지_제작_자료전달_가이드.md`](../다른페이지_제작_자료전달_가이드.md)에 있다.

## 8. 마지막 확인 문장

프롬프트 끝에 다음 한 줄을 붙이면 결과 보고의 누락을 줄일 수 있다.

> “완료 후 ‘무엇을 확인했는지, 무엇을 변경했는지, 원본 데이터와 디자인이 유지됐는지, 무엇을 실제로 검증했는지’를 근거와 함께 보고해줘.”

프롬프트만으로 실수를 완전히 막을 수는 없다. 중요한 작업은 **작업 전 원본 수치와 경로 기록 → 제한된 파일 수정 → Git 차이 확인 → 실제 동작 검증**까지 요청하는 것이 핵심이다.

## 9. 밀도·그리드·좌측 정렬을 UI로 요청하는 법

[`밀도·그리드·좌측 정렬 UI 검토안`](../디자인시스템/밀도_그리드_좌측정렬_검토/index.html)은 관리자/사용자 화면, 간격 비교, 정렬선, 6개 UI 스켈레톤을 직접 보여준다. 이 화면은 **검토용 시안**이다. 현행 기준 화면인 `디자인시스템/index.html` 및 관련 기능 문서와 함께 비교하고, 실제 개발에는 확정된 원본 데이터만 쓴다.

산출물 페이지의 **UI 설명 프롬프트** 탭에서는 요청 문장과 UI 검토 화면을 나란히 볼 수 있다. 오른쪽 미리보기는 **UI 검토 화면 / UI 패턴 예시**로 전환할 수 있다.

“밀도 있게”, “그리드로”, “좌측 정렬로”만 적으면 AI마다 해석이 달라진다. 아래 여섯 항목을 함께 지정한다.

| 말할 항목 | 구체적인 설명 예시 |
|---|---|
| 화면 목적 | 운영자가 여러 건을 검색·비교·처리 / 사용자가 내용을 이해하고 신청 |
| 구조 | 헤더 1줄, 검색조건 4열, 결과 표 + 우측 상세 / 제목 + 핵심 정보 4열 |
| 밀도 | 반복 제목·큰 내부 여백·빈 설명 영역을 먼저 줄임. 글자와 조작 영역은 임의 축소 금지 |
| 정렬 | 제목·라벨·본문·표 문자는 좌측 시작선을 맞춤. 상태·주요 행동은 정해진 위치 |
| 데이터와 기능 | 어느 파일의 어떤 필드를 사용하고, 검색·선택·저장 등의 동작을 어느 문서에 맞출지 |
| 검수 | 동일 너비 전후 비교, 데스크톱/모바일 겹침, 원본 항목·값 보존, 실제 동작 |

### A. 스켈레톤만 먼저 제안받기

```text
작업 모드: 분석·시안만. 운영 파일과 데이터를 수정하지 마.
화면 목적: [예: 관리자가 신청 건을 검색·비교·처리]
현행 기준: 디자인시스템/index.html
선호 시각 기준: 디자인시스템/밀도_그리드_좌측정렬_검토/index.html
관련 문서: 디자인시스템/docs/재사용_디자인_프롬프트/공통/01_화면목적_정보우선순위_기준.md,
  디자인시스템/docs/재사용_디자인_프롬프트/공통/03_다단구조_밀도_간격_기준.md

현행 화면과 문서를 읽고 화면 목적에 맞는 스켈레톤 2안을 제시해줘.
각 안에 헤더, 필터, 목록/카드, 상세/폼, 주요 행동의 위치와 열 수를 표시해줘.
제목·라벨·값의 좌측 시작선을 어떻게 맞출지 설명해줘.
밀도는 반복 제목, 중복 테두리, 큰 여백을 정리해서 높이고 글자 크기만 일괄 축소하지 마.
현행 기준과 다른 부분, 가독성·접근성에서 확인할 부분을 항목별로 적어줘.
스켈레톤에는 실제 자료처럼 보이는 임의 수치를 넣지 말고 '예시'라고 표시해줘.
```

### B. 관리자 화면을 구체적으로 설명하기

```text
작업 모드: 범위 내 신규 화면 구현
화면 목적: [관리자가 무엇을 찾고, 비교하고, 처리하는지]
원본 데이터: [정확한 파일 경로와 사용할 필드]
기능 기준: [검색·선택·상세·저장·다운로드에 해당하는 문서와 파일 경로]
현행 디자인 기준: 디자인시스템/index.html, 디자인시스템/layout.css
검토 시안: 디자인시스템/밀도_그리드_좌측정렬_검토/index.html
수정 허용: [새 화면 폴더]

헤더에는 업무명·건수·현재 상태·주요 행동을 한 줄로 배치해줘.
검색조건은 짧은 항목 4열을 우선하고, 결과는 비교 가능한 표로 보여줘.
행 선택 시 우측 상세에서 식별정보와 처리 행동을 같은 위치에 유지해줘.
제목·필터 라벨·표 문자·상세 값은 좌측 시작선을 맞춰줘.
반복 제목과 카드 내부 여백을 줄여 첫 화면에 필터와 결과 첫 행이 보이게 해줘.
좁은 화면의 표는 핵심 열을 남기고 가로 스크롤을 허용해줘.
원본 항목 수와 값, 상태 의미, 날짜, 파일 경로를 임의로 수정하지 마.
완료 후 실제 연결 기능과 예시/미연결 기능을 구분해 보고해줘.
```

### C. 사용자 안내·랜딩 화면을 구체적으로 설명하기

```text
작업 모드: 범위 내 신규 화면 구현
화면 목적: [방문자가 무엇을 이해하고 어떤 행동을 해야 하는지]
콘텐츠 원천: [정확한 파일 경로]
관련 기능 문서: [신청·상담·로그인·결제 등 실제로 연결할 문서 경로]
현행 디자인 기준: 디자인시스템/index.html
검토 시안: 디자인시스템/밀도_그리드_좌측정렬_검토/index.html

제목·핵심 설명·첫 번째 행동 버튼을 좌측 정렬해줘.
대상·일정·방식처럼 짧은 안내는 같은 높이의 정보 그리드로 묶어줘.
긴 설명은 읽는 순서를 유지하도록 1열로 두고, 사용자 본문 가독성을 유지해줘.
자료에 없는 과정명·가격·일정·혜택·후기를 만들어 넣지 마.
신청 버튼의 도착지와 필요한 기능 문서를 확인하고, 연결되지 않은 버튼은 명시해줘.
완료 후 원본 문구·숫자·링크의 대조표와 데스크톱/모바일 확인 결과를 제출해줘.
```

### D. 현행 디자인과 새 시안을 비교하고 확정하기

```text
작업 모드: 읽기만. 이번에는 구현 파일을 수정하지 마.
비교 대상: 디자인시스템/index.html, 디자인시스템/밀도_그리드_좌측정렬_검토/index.html
검토 화면: [관리자 업무 / 사용자 안내]

같은 화면 목적을 기준으로 정보 밀도, 그리드 열 수, 좌측 시작선, 상태·행동 위치,
가독성, 좁은 화면 대응을 비교표로 정리해줘.
각 차이가 현행 디자인 기준의 연장인지 새로운 변경 제안인지 표시해줘.
대표님께 결정받아야 할 항목만 3~5개로 압축하고, 각 항목은 화면에서 확인할 위치를 적어줘.
샘플 화면의 가상 정보는 실제 서비스 데이터로 판단하지 마.
```

### E. 원하는 UI 패턴의 모양과 동작을 지정하기

사이드바, 경로·헤더, 요약 카드, 인라인 Drawer, 페이지 이동, 알림, 빈 결과·로딩, 단계 표시와 탭·접기·펼치기·필터·표·상세·폼·대화상자의 **실제 모양과 상태 변화**는 산출물 페이지의 [`UI 패턴 예시` 탭](../index.html#ui-pattern-panel)에서 눌러볼 수 있다. 회색 스켈레톤은 배치 참고용이며, 실제 UI 동작을 설명할 때는 아래처럼 패턴과 반응을 함께 적는다.

```text
작업 모드: [시안만 / 범위 내 구현]
화면 목적: [사용자가 이 화면에서 끝내야 할 일]
참고 화면: 디자인시스템/밀도_그리드_좌측정렬_검토/index.html?view=patterns
사용할 UI 패턴: [사이드바 / 경로·헤더 / 요약 카드 / 인라인 Drawer / 페이지 이동 /
  알림 / 빈 결과·로딩 / 단계 표시 / 탭 / 접기·펼치기 / 필터·상태 칩 /
  표·상세 / 입력 폼 / 대화상자 중 필요한 것]
실제 데이터 원천: [파일 경로와 필드]
기능 기준 문서: [검색·선택·신청·저장·확인 동작의 원문 경로]

선택한 UI 패턴마다 다음을 표로 먼저 정리해줘.
1. 화면에 보이는 모양과 위치: 탭 이름, 열 수, 시작선, 상태 색상, 버튼 위치
2. 기본 상태: 처음 선택된 탭, 접힌 영역, 필터 선택값, 빈 결과 표시
3. 사용자 동작: 무엇을 누르면 어느 영역과 건수가 어떻게 바뀌는지
4. 데이터·기능 연결: 화면 표시값의 원본 필드와 실제 실행할 기능 문서
5. 예외·검증: 값 없음, 오류, 좁은 화면, 키보드 조작, 원본 대조

예를 들어 사이드바는 '회원 관리' 아래 하위 메뉴를 접고 펼치며 현재 메뉴를 강조해줘.
경로·헤더는 화면명·건수·상태·주요 행동을 같은 시작선과 정해진 위치에 둬.
인라인 Drawer는 목록 옆에서 열고 닫히며, 닫으면 목록이 전체 폭을 다시 쓰게 해줘.
페이지 이동은 현재 페이지·전체 건수·이전/다음 상태를 목록과 함께 갱신해줘.
빈 결과와 로딩은 서로 다른 문구와 행동으로 구분해줘.
탭은 '과정 개요·일정·신청 안내'로 나누고 선택한 본문만 보여줘.
필터 칩은 선택 상태를 표시하고 결과 행과 건수를 함께 갱신해줘.
표에서 행을 선택하면 오른쪽 상세의 식별값과 상태가 그 행으로 바뀌게 해줘.
자료나 문서에 없는 동작은 구현된 것처럼 표시하지 말고 미연결이라고 적어줘.
기준 파일의 색상·타이포그래피·접근성 크기는 승인 없이 변경하지 마.
```

## 사이트 표시 내용 갱신

이 문서를 수정한 뒤에는 저장소 루트에서 `node scripts/build-prompt-guide.js`를 실행한다. 생성되는 `AI_작업요청_프롬프트_가이드/content.js`가 메인 페이지의 **프롬프트 제시 가이드** 탭에 표시되는 본문이다. `node scripts/build-prompt-guide.js --check`로 문서와 표시 내용의 일치 여부를 확인할 수 있다.
