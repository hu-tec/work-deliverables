# 보안 프롬프트: 웹서비스 소스·기능·운영 흐름 점검

**이 탭의 용도:** 개발된 웹서비스의 보안 설계와 납품 소스를 근거로 점검·수정·재검증을 요청한다. `[대괄호]`에는 실제 저장소, 서비스 범위, 테스트 환경, 승인된 기능 문서를 넣는다. 자격증 발급은 여러 적용 사례 중 하나이며, 일반 웹서비스 점검 범위를 그 사례로 제한하지 않는다.

## 먼저 정할 점검 범위

| 구분 | 확인할 자료 | 결과에서 구분할 것 |
|---|---|---|
| 구현 범위 | 저장소 경로·커밋, 프론트엔드·서버·API·DB·배포 설정 | 실제 구현과 문서상 예정 기능 |
| 사용자와 권한 | 일반 사용자·관리자·운영자 역할, 접근 가능한 데이터·작업 | 로그인 성공과 대상별 권한 확인 |
| 데이터와 외부 연동 | 개인정보, 파일, 결제·본인확인·메일 등 외부 서비스 | 직접 처리, 위탁·제공, 로그·백업에 남는 정보 |
| 실행 가능 범위 | 테스트 URL, 합성 계정, 허용된 검사 방법 | 실제 재현, 도구 결과, 코드상 추정, 미검증 |

보안 점검은 **코드에 방어 로직이 있는지**와 **실행 환경에서 그 로직이 작동하는지**를 구분한다. 실서비스에 영향을 주는 공격·대량 요청·데이터 변경은 명시된 테스트 범위 없이 수행하지 않는다. 법령 적용 판단은 [10번 개인정보·보안 법령·기준](../../index.html#legal-privacy), 스킬 사용법은 [11번 보안 점검](../../index.html#skill-security)에서 별도로 확인한다.

## 프롬프트 1. 납품 소스의 보안 범위와 데이터 흐름 파악

```text
작업 모드: 읽기만. 파일·DB·운영 설정·실제 데이터를 수정하지 마.
대상 저장소/커밋: [정확한 경로·해시]
설치·실행 문서와 테스트 URL: [경로·주소]
기능 정의·권한표·데이터 정책: [승인 문서]

1. 실제 사용 언어·프레임워크, 브라우저·서버·API·DB·파일 저장소·외부 연동을 파일 근거와 함께 정리해줘.
2. 로그인, 비밀번호 재설정, 관리자 기능, 조회·다운로드·업로드, 결제 또는 본인확인처럼 해당 서비스에 존재하는 흐름을 목록으로 만들어줘.
3. 사용자 역할별로 어떤 데이터와 작업에 접근하는지 실제 라우트·핸들러·권한 검사 위치와 연결해줘.
4. 개인정보·비밀값이 입력 → 전송 → 저장 → 응답 → 로그·분석 → 백업 → 파기로 이동하는 경로를 그려줘. 실제 값 자체를 출력하지 마.
5. 소스와 실행 화면이 같은 버전인지 확인하고, 접근 권한이나 환경 부족으로 확인하지 못한 구성 요소를 표시해줘.

결과 표: 구성 요소/흐름 | 소스 위치 | 데이터·권한 | 기존 통제 | 실제 확인 방법 | 미확인 사항.
이 단계에서는 취약점을 단정하지 말고 다음 점검의 범위와 우선순위를 제안해줘.
```

## 프롬프트 2. 웹서비스 보안 진단과 HTML 리포트

```text
작업 모드: 점검 대상은 읽기만. 소스·DB·운영 데이터를 수정하지 마. 지정한 HTML 리포트 파일만 새로 작성해줘.
대상 저장소/커밋: [정확한 경로·해시]
허용된 테스트 환경과 합성 계정: [주소·역할·허용 범위]
기능 정의·권한표·배포 구성: [승인 문서]
HTML 리포트 저장 경로: [예: reports/보안_점검_리포트.html]

1. 사용 가능한 보안 스킬·검사 도구와 적용 범위를 확인하고, 실제 사용한 이름·버전을 기록해줘. 없으면 사용했다고 쓰지 마.
2. 인증·세션 관리, 사용자·관리자 권한, 대상별 접근 제어, 입력 검증·출력 처리, 파일 업로드·다운로드, 비밀값·환경 설정, 오류·로그·백업, 외부 연동을 서비스에 존재하는 기능에 맞춰 확인해줘.
3. 브라우저에서 버튼을 숨긴 것과 서버에서 권한을 검증한 것을 구분해줘. 다른 사용자·조직·항목의 데이터 접근 가능성은 합성 데이터와 허용된 환경에서만 재현해줘.
4. 의존성·설정 검사 도구를 쓸 수 있으면 사용한 데이터베이스/시점과 결과를 적고, 발견 항목이 실제 사용 경로에 영향을 주는지 별도로 검토해줘.
5. OWASP ASVS와 해당 언어·프레임워크의 공식 보안 문서를 참고하되, 조항 번호를 확인하지 못하면 임의로 만들지 마. 법적 적합성과 인증 취득 여부는 기술 진단과 분리해줘.
6. 발견 사항마다 파일·줄 번호, 실행 재현 또는 코드 근거, 전제 조건, 영향받는 자산, 심각도 이유, 수정안과 재검증 방법을 적어줘. 도구 경고만 있는 항목은 '추가 확인 필요'로 표시해줘.
7. 실서비스 공격, 대량 요청, 실제 개인정보 열람·출력, 비밀값 공개는 하지 마. 수행하지 못한 검사는 미검증으로 남겨줘.

결과를 지정한 경로의 단독 실행 가능한 한국어 HTML 리포트로 저장해줘.
필수 섹션: 대상·버전·점검일·환경 / 적용 범위와 방법 / 위험도별 요약 /
발견 사항별 증거·영향·수정·재검증 / 미검증 항목·운영 확인 질문 / 참고 기준.
표에는 제목 셀을 쓰고 좁은 화면과 인쇄에서 읽히게 해줘. 개인정보·토큰·비밀번호·키 원문은 HTML과 증거 링크에 넣지 마.
마지막 답변에는 리포트 경로와 즉시 조치할 항목만 짧게 알려줘.
```

## 프롬프트 3. 개인정보·비밀값 저장 경로만 집중 점검

```text
작업 모드: 읽기만. 실제 개인정보와 비밀값은 표시하지 마.
대상 저장소/커밋: [경로·해시]
데이터 항목·보유기간·권한표: [승인 문서]
외부 서비스·수탁사·클라우드 구성: [확정 문서]

입력 폼·API·DB 스키마·파일·URL·브라우저 저장소·로그·오류 추적·분석 도구·백업을 따라 데이터 흐름을 확인해줘.
각 필드의 목적·처리 근거·저장 위치·접근 역할·암호화·보유 종료 조건·파기 경로를 표로 정리해줘.
하드코딩된 키·토큰, 환경 파일·배포 설정, 로그에 남는 인증 응답이 있는지 값 자체를 출력하지 말고 위치와 위험만 알려줘.
검토 결과를 '소스에서 확인/실행에서 확인/문서에만 존재/미검증'으로 구분해줘.
법령 적용 여부와 보유기간 결정은 승인된 정책과 현행 법령을 대조할 담당자 항목으로 남겨줘.
```

## 프롬프트 4. 저장소 근거로 위협 모델링

```text
작업 모드: 읽기·분석만. 공격을 실행하거나 운영 상태를 바꾸지 마.
대상 범위: [서비스·저장소 경로·커밋]
배포 방식과 외부 노출: [확인 문서 또는 미확인]
사용자 역할·민감 데이터·외부 연동: [확정 문서]

현재 환경에 security-threat-model 스킬이 활성화되어 있으면 해당 SKILL.md 절차를 따라줘. 없으면 미사용을 명시하고 일반적인 위협 모델링을 진행해줘.
구성 요소, 데이터 자산, 신뢰 경계, 진입점, 기존 보안 통제를 소스 파일·설정 근거로 정리해줘.
현실적인 공격자 목표와 남용 경로를 소수의 우선순위로 제시하고, 확인된 사실과 배포·운영에 대한 가정을 분리해줘.
각 경로에 예상 영향, 이미 있는 통제, 남은 위험, 구체적인 확인·개선 위치를 연결해줘.
서비스 맥락이 없어서 우선순위가 달라질 수 있으면 필요한 질문을 먼저 적어줘.
```

## 프롬프트 5. 수정 후 같은 범위로 재검증

```text
작업 모드: 읽기·검증만. 운영 데이터나 배포 설정을 변경하지 마.
이전 보안 리포트: [HTML 경로]
수정 전/후 커밋과 테스트 URL: [정확한 값]
재검증 허용 범위와 합성 계정: [정확한 값]
HTML 재검증 리포트 저장 경로: [예: reports/보안_재검증_리포트.html]

이전 발견 ID별로 같은 전제 조건과 테스트 환경에서 다시 확인해줘.
각 항목을 '해결/부분 해결/변화 없음/악화/확인 불가'로 구분하고, 수정 전후 파일·줄 번호와 실제 재현 증거를 연결해줘.
공통 인증·권한·입력 처리의 변경으로 다른 사용자 흐름이 깨지지 않았는지도 확인해줘.
결과를 한국어 HTML 리포트로 저장하고 남은 위험, 미검증 범위, 배포 전 결정 사항을 명시해줘.
```

## 특수 업무 사례

주민등록번호 없이 본인확인하고 자격증을 발급하는 서비스는 [개인정보·자격증 발급 사례 프롬프트](개인정보_자격증발급_프롬프트.md)를 추가로 참고한다. 해당 사례의 데이터 항목·발급 규칙을 다른 서비스에 그대로 적용하지 않는다.
