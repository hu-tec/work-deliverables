# 개인정보 보호: 주민등록번호 없이 본인확인·자격증 발급

**이 탭의 용도:** 주민등록번호 입력·저장 없이 온라인 자격증을 신청, 발급, 조회, 재발급하는 절차를 설계할 때 사용한다. 여기의 흐름은 **설계 예시**이며, 자격증 종류·발급 주체·근거 법령·기존 보유 자료에 맞춰 법무·개인정보보호책임자가 처리 근거와 보유기간을 확정해야 한다.

## 먼저 구분할 세 가지

1. **본인확인:** 지금 신청하는 사람이 누구인지 지정된 본인확인기관의 서비스로 확인한다.
2. **발급 자격 확인:** 그 사람이 시험 합격·교육 수료·회원 상태 등 발급 조건을 충족했는지 발급기관의 **확정된 원장**과 대조한다. 본인확인 성공만으로 자격이 생기지 않는다.
3. **증명서 진위 확인:** 이미 발급된 증명서가 유효한지 제3자가 확인한다. 이때 신청자의 개인정보를 필요 이상으로 공개하지 않는다.

국가법령정보센터에 게시된 개인정보 보호법 제24조의2는 정해진 예외 외의 주민등록번호 처리를 제한한다. 본인확인기관의 대체수단을 이용하면 이용 기관이 직접 주민등록번호 입력창을 둘 필요가 없는 설계를 할 수 있다. KISA는 휴대폰·아이핀·신용카드·인증서 등을 대체수단으로 소개한다. **대체수단을 쓴다는 사실만으로 다른 개인정보 처리의 적법성이 자동 확보되지는 않는다.** [개인정보 보호법 제24조의2](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1029335165) · [KISA 본인확인 대체수단](https://identity.kisa.or.kr/web/main/contents/M010-04)

## 권장 절차 예시

| 단계 | 사용자·시스템의 동작 | 서비스가 확인·기록할 것 |
|---|---|---|
| 1. 신청 시작 | 로그인한 사용자가 발급 목적과 처리 안내를 확인 | 신청 목적, 필요한 최소 항목, 처리 근거, 보유기간, 수탁/제공 관계, 문의 경로를 확정 |
| 2. 본인확인 | 사용자가 지정된 본인확인기관의 화면으로 이동 | 서버가 일회성 요청 식별자와 만료시간을 만들고 신청 세션과 묶음 |
| 3. 결과 검증 | 기관이 결과를 돌려주면 서버가 진위를 확인 | 서명/암호화 응답, 요청 식별자, 유효기간, 재사용 여부, 성공 상태를 기관 규격에 따라 검증 |
| 4. 최소 정보 매칭 | 검증된 결과와 내부 발급 대상 원장을 연결 | 내부 사용자·수험·수료 식별자를 우선 사용. 같은 이름만으로 자동 일치 처리하지 않음 |
| 5. 자격 심사 | 합격·수료·결격·취소 등 확정 규칙 확인 | 원장 출처, 적용 기준일, 결과와 예외 사유를 기록. 불일치는 수동 심사로 보냄 |
| 6. 발급 | 발급 번호를 만들고 문서/PDF를 제공 | 표시 항목을 최소화하고, 접근 권한·다운로드 만료·재발급·취소 규칙을 적용 |
| 7. 진위 조회 | 번호/QR로 발급 상태 확인 | 공개 조회에는 유효/취소·발급 주체·자격명 등 필요한 최소 정보만 노출 |
| 8. 보관·파기 | 처리 목적 종료·보유기간 도래 시 정리 | 본인확인 응답 원문, 발급 로그, 증명서 파일별 보관·삭제 정책을 적용 |

**CI/DI 주의:** KISA는 CI(연계정보)와 DI(중복가입 방지정보)를 본인확인 결과정보로 설명한다. 둘 다 자동으로 받아 장기 보관하는 기본값으로 삼지 않는다. 현재 발급 원장과 매칭하는 데 필요한지, 처리 근거·제공 계약·보유기간이 무엇인지 먼저 판단한다. 내부 발급번호와 계정 식별자로 충분하다면 그쪽을 우선 검토한다. [KISA 본인확인 용어](https://identity.kisa.or.kr/web/main/contents/M010-05)

**기존 원장 주의:** 예전 자료의 식별 방식이 다르면 임의의 이름·생년월일 조합으로 자동 합치지 않는다. 동명이인, 개명, 휴대폰 명의 변경, 미성년자·대리 신청, 과거 정보 누락을 예외 흐름으로 설계한다. 대리 발급은 위임 근거와 권한 확인이 확정되기 전까지 자동 처리하지 않는다.

## 최소 데이터 설계 예시

| 정보 | 기본 판단 | 이유·확인 사항 |
|---|---|---|
| 주민등록번호 | 이용 기관 입력·저장·로그에서 제외 | 법령상 예외가 실제로 있는지 별도 확인. 직접 수집 없이 가능한 흐름 우선 |
| 내부 사용자/수험/수료 ID | 필요한 범위에서 사용 | 발급 원장의 특정 행과 연결하는 기본 키 |
| 본인확인 성공 여부·거래 식별자 | 필요한 증빙 기간만 기록 | 결과 위조·재사용 조사에 필요한 최소 기록 범위 확정 |
| 이름·생년월일 | 매칭에 필요한 항목만 검토 | 동명이인 방지에 충분한지, 보관이 꼭 필요한지 별도 판단 |
| CI/DI | 필요성·법적 근거·계약 확인 후 결정 | 단순히 공급자가 제공한다는 이유로 저장하지 않음 |
| 증명서 표시 항목·QR 응답 | 검증 목적에 필요한 값만 공개 | 공개 URL에서 생년월일·연락처 등이 유출되지 않게 확인 |

## 프롬프트 1. 처리 근거와 보유 데이터부터 조사

```text
작업 모드: 읽기만. 코드·DB·운영 데이터를 수정하지 마.
서비스/자격증 종류: [정확한 명칭과 발급 주체]
관련 법령·정관·운영 규칙: [확정된 문서 경로 또는 확인 필요]
현재 회원·시험·수료·발급 원장: [테이블/파일과 필드]
현재 본인확인 계약/응답 규격: [문서 경로 또는 미정]

주민등록번호 없이 온라인 자격증을 발급할 수 있는지 현황을 조사해줘.
1. 현재 입력폼, DB, API, 로그, 분석도구, 파일/백업에서 주민등록번호 또는 그 파생값의 흐름을 찾아줘.
2. 각 개인정보 항목을 수집 목적, 처리 근거, 제공·위탁 관계, 저장 위치, 보유기간, 파기 시점으로 표로 정리해줘.
3. 본인확인과 발급 자격 확인에 각각 필요한 최소 항목을 구분해줘.
4. CI/DI를 쓴다면 필요한 이유와 대체 가능한 내부 키를 비교해줘. 필요성이 불분명하면 기본적으로 수집 제안에 넣지 마.
5. 법령상 주민등록번호 처리 예외 또는 자격증별 별도 법적 의무가 있는지 공식 원문으로 확인하고, 불명확하면 법무/개인정보보호책임자 결정사항으로 남겨줘.
6. 원장 매칭이 불가능한 과거 자료와 동명이인·개명·대리 신청 예외를 별도 목록으로 만들어줘.

결과: 현행 데이터 흐름도, 제거·유지·결정 필요 항목 표, 확정 전에는 구현하면 안 되는 쟁점.
```

## 프롬프트 2. 사용자 절차와 화면·기능 문서 설계

```text
작업 모드: 검토·제안만. 운영 데이터와 코드는 수정하지 마.
대상 사용자: [응시자/수료자/회원 등]
발급 조건 근거: [시험·교육·결격 규칙 문서]
본인확인 방식: [계약된 본인확인기관/수단 또는 선정 필요]
표시할 증명서 항목: [확정된 항목 또는 결정 필요]
기준 디자인시스템: [정확한 파일 경로]

신청 → 본인확인 → 발급 원장 대조 → 발급 심사 → 문서 다운로드 → 진위 조회 → 재발급/취소 흐름을 설계해줘.
각 단계마다 화면 이름, 사용자 행동, 서버 검증, 필요한 최소 데이터, 성공/실패/재시도/상담 전환 상태를 적어줘.
본인확인 성공과 발급 자격 충족을 별도 판정으로 표시해줘.
같은 이름만으로 원장을 자동 매칭하지 말고, 확인된 내부 키와 예외 심사 경로를 제안해줘.
공개 QR/검증 페이지의 노출 필드를 최소화하고 증명서 번호 추측·대량 조회 방지 방안을 넣어줘.
현행 디자인 색상·타이포·간격을 임의로 바꾸지 마.
결과: 화면 목록, 상태 전이표, 필드 목록, 권한표, 미결정 정책 질문.
```

## 프롬프트 3. 구현 전 보안 설계와 개발 요청

```text
작업 모드: [검토·제안만 / 범위 내 구현]
수정 허용 파일: [정확한 경로 또는 없음]
본인확인기관 연동 규격: [계약된 공식 문서]
발급 원장과 식별키: [확정된 필드]
발급·취소·재발급 규칙: [승인된 정책 문서]
보호: 실제 개인정보, 원본 합격/수료 기록, 현행 디자인, 다른 서비스의 인증 흐름

다음 위협과 통제 방법을 설계하고 승인된 범위만 구현해줘:
- 위조·재사용된 본인확인 결과: 서버측 진위 검증, 요청-응답 연결, 만료·1회 사용 확인
- 다른 사람의 자격증 발급/다운로드: 계정·본인확인·원장 식별자 대조, 객체 단위 권한 확인
- 발급 번호/QR 추측과 대량 조회: 예측 곤란한 토큰, 조회 제한, 최소 응답
- 인증 결과·개인정보의 URL/로그/분석도구 유출: 저장·로그 필드 제한과 비밀값 관리
- 동시 신청·중복 발급·취소 후 재발급: 서버측 중복 제어와 상태 이력

테스트에는 합성 데이터만 사용하고, 실제 주민등록번호·CI/DI·인증 응답을 예시 코드나 로그에 넣지 마.
완료 보고에는 변경 파일, 데이터 흐름, 권한별 검증, 실패 사례, 실제 수행한 테스트와 미검증 항목을 분리해줘.
```

## 프롬프트 4. 발급 전 개인정보·보안 검수

```text
작업 모드: 읽기만. 배포·운영 데이터 변경은 하지 마.
대상 환경: [테스트 환경 URL/경로]
검수 기준: [승인된 개인정보 처리방침·보유기간·발급 규칙·기관 연동 문서]

합성 계정으로 정상 발급, 자격 미충족, 본인확인 실패/만료/재사용,
동명이인·개명·원장 미연결, 타인 증명서 접근, 취소·재발급, QR 대량 조회를 점검해줘.
폼·요청·응답·DB·로그·분석도구·백업 중 이용 기관이 주민등록번호를 받거나 남기는 곳이 없는지 확인해줘.
CI/DI와 본인확인 원문이 저장된다면 승인된 필요성·기간·권한과 일치하는지 확인해줘.
결과 표: 시나리오 | 기대 결과 | 실제 결과 | 증거 위치 | 위험도 | 수정 필요 | 재검증 방법.
법적 적합성·품질인증을 기술 테스트만으로 확정하지 말고 담당 검토 사항으로 표시해줘.
```
