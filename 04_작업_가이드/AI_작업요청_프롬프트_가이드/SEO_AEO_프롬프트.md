# SEO·AEO: 검색 발견성과 답변에 쓰일 수 있는 콘텐츠

**이 탭의 용도:** 새 랜딩페이지나 기존 페이지의 검색 노출 준비 상태를 살펴보고, 확인된 원문만으로 사용자 질문에 답하기 쉬운 구조를 만들 때 사용한다. `[대괄호]`를 실제 경로와 내용으로 바꾼다.

## SEO와 AEO를 함께 보는 방법

**SEO**는 검색엔진이 페이지를 발견·크롤링·색인하고 사용자가 필요한 내용을 찾도록 만드는 작업이다. **AEO(Answer Engine Optimization)**는 사용자의 질문에 대해 페이지가 명확한 답과 근거를 제공하도록 구성하는 실무적 관점이다. AEO는 검색엔진이 보장하는 별도 인증이나 노출 공식이 아니다.

Google은 AI 검색 기능에도 기본 SEO 모범 사례가 유효하며, AI Overviews·AI Mode에 표시되기 위한 별도의 특별한 최적화는 필요하지 않다고 안내한다. 색인 가능하고 검색 결과의 스니펫으로 표시될 수 있는 페이지여야 지원 링크로 노출될 자격이 있지만, 요건을 충족해도 노출은 보장되지 않는다. [Google AI 기능 안내](https://developers.google.com/search/docs/appearance/ai-features)

| 층위 | 확인할 것 | 피해야 할 것 |
|---|---|---|
| 검색 접근 | 공개 URL, 상태 코드, robots/noindex, 내부 링크, 사이트맵, canonical, JS 렌더링 | 검색봇이 보지 못하는 핵심 본문을 방치 |
| 페이지 의미 | 고유한 제목·설명, H1과 소제목, 실제 서비스와 일치하는 본문 | 모든 페이지에 같은 제목, 키워드 반복 |
| 답변 가능성 | 자주 묻는 질문에 대한 직접적인 답, 조건·절차·제외 사항, 갱신일과 책임 주체 | 근거 없는 수치·효과·FAQ를 새로 지어냄 |
| 구조화 데이터 | 지원되는 유형만 사용하고 화면에 보이는 사실과 일치시키기 | AI 노출을 보장한다는 이유로 임의의 스키마를 추가 |
| 검증 | 실제 공개 URL의 색인·렌더링·검색 성과 확인 | 로컬 코드만 보고 검색 성과를 단정 |

이 저장소에서는 새 랜딩페이지를 만들 때 **원본 HTML뿐 아니라 `data.js`, `content.js` 등 표시 내용을 공급하는 파일과 실제 렌더링 화면**을 함께 확인한다. 확정되지 않은 행사일·수료 조건·자격증 명칭·비용을 검색용 문구에 추가하지 않는다.

## 프롬프트 1. SEO·AEO 현황을 수정 없이 진단

```text
작업 모드: 읽기만. 파일을 수정하지 마.
대상 공개 URL: [정확한 URL]
대상 로컬 소스: [정확한 폴더/파일]
우선 사용자 질문: [예: 신청 자격은? 교육 일정은? 자격증은 어떻게 발급받나?]
원본 사실 자료: [확정된 기획/운영/정책 문서 경로]

공개 URL과 로컬 소스의 차이를 먼저 확인해줘.
1. 공개 접근성: 상태 코드, robots/noindex, canonical, 사이트맵·내부 링크, 모바일 화면을 확인해줘.
2. 렌더링: HTML 원문과 JS 실행 후 본문·링크가 어떻게 다른지 확인해줘.
3. 페이지별 title, meta description, H1~H3, 본문 중복과 누락을 표로 만들어줘.
4. 위 사용자 질문 각각에 대해 '페이지에서 직접 답하는 위치 / 근거 문서 / 부족한 정보'를 매핑해줘.
5. 구조화 데이터가 있으면 화면에 보이는 사실과 일치하는지, 지원 유형인지 확인해줘.
6. 각 제안에 예상 효과를 단정하지 말고 우선순위와 검증 방법을 적어줘.

결과 표: URL | 사용자 의도 | 현재 근거 | 문제/확인 필요 | 제안 | 변경 대상 파일 | 검증 방법.
확인 불가능한 검색 콘솔·색인 상태는 '접근 권한 필요'로 표시해줘.
```

## 프롬프트 2. 원본 데이터를 대조하며 새 랜딩페이지 제작

```text
작업 모드: 범위 내 구현
원본 랜딩: [ver1의 HTML·JS·CSS·이미지 경로 전체]
새 랜딩 위치: [ver2의 새 폴더/파일]
확정 원문: [문구·조건·가격·일정·링크의 기준 파일]
디자인 기준: [현재 디자인시스템의 정확한 화면/문서]
변경 허용: [레이아웃·메타데이터·질문형 소제목 등 정확한 범위]
보호: 원본 수치·일정·자격 조건·기관명·다운로드 링크·신청 동작

구현 전에 원본 화면에 실제 표시되는 모든 콘텐츠를 HTML과 데이터/스크립트 파일에서 수집해줘.
각 항목을 '그대로 이전 / 표현만 수정 / 제외 승인 필요'로 표시한 대조표를 먼저 작성해줘.
새 페이지는 사용자가 찾는 질문에 대해 확인된 사실을 본문 안에서 직접 설명하되,
원문에 없는 답·FAQ·후기·통계를 만들어 넣지 마.
고유한 title·description·H1, 읽기 쉬운 제목 구조, 크롤링 가능한 링크와 공개 URL을 구성해줘.
구조화 데이터는 화면에 보이는 내용과 일치하고 해당 검색엔진이 지원하는 유형일 때만 제안/적용해줘.

완료 기준: 원본 항목·수치·날짜·링크의 전후 대조, 공개 화면/JS 렌더링 확인,
모바일·키보드 사용, 메타데이터·canonical·robots 상태 확인.
보고: 변경 파일, 대조표, 실제 검증 결과, 검색 콘솔 등 미검증 항목.
```

## 프롬프트 3. AEO 관점으로 설명을 보강하되 사실을 추가하지 않기

```text
작업 모드: 검토·제안만. 페이지를 수정하지 마.
대상 페이지: [URL/파일]
확정 사실 자료: [정책·기능 정의·가격표·일정표 등 경로]
답해야 할 질문: [사용자가 실제로 할 질문 5~10개]

각 질문에 대해 현재 페이지에 답이 있는지 찾아 '있음 / 일부 / 없음'으로 분류해줘.
답이 있으면 정확한 출처와 짧은 답, 예외·조건, 연결할 내부 페이지를 제안해줘.
답이 없으면 추측하지 말고 담당자가 확인해야 할 질문으로 남겨줘.
새 FAQ가 정말 필요한지 판단하고, 단순 키워드 반복보다 실제 사용자 의도에 맞는 위치를 제안해줘.
기관명, 서비스명, 자격 요건, 발급 주체, 수수료, 시행일 같은 사실은 원본과 대조해줘.
결과: 질문 | 현재 답 위치 | 원본 근거 | 제안 문구 | 확인 필요 사항 | 편집 권한자.
```

## 프롬프트 4. 배포 뒤 측정·검증 계획

```text
작업 모드: 검토·제안만. 검색 순위나 AI 인용을 보장한다고 쓰지 마.
대상 URL 목록: [공개 URL들]
변경일: [날짜]

페이지별로 색인 가능 여부, Google Search Console URL 검사, 실제 렌더링된 본문,
사이트맵·내부 링크, 구조화 데이터 유효성, 검색 유입 질의와 클릭을 확인하는 순서를 제안해줘.
변경 전/후 비교 시 기간·계절성·다른 변경을 함께 기록하게 해줘.
AI 답변에 등장하는지 관찰하더라도 검색엔진별·질의별 편차를 표시하고 성과를 단정하지 마.
결과: 담당자, 도구, 확인 시점, 기대 관찰값, 실패 시 재진단 순서.
```
