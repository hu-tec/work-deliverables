# 디자인·그리드·밀도 점검: Computer Use로 화면 보기

**이 탭의 용도:** 개발된 화면을 실제 창에서 하나씩 확인하고, 요청한 촘촘함·그리드·좌측 정렬이 구현됐는지 근거를 남긴다. 이 저장소에는 Windows 앱 화면을 관찰·조작하는 `computer-use` 스킬이 제공된다. 다른 실행 환경에서는 사용 가능 여부를 먼저 확인한다.

**우선순위:** 현재 요청과 승인된 화면·기능 정의를 먼저 적용한다. UI 검토안은 밀도 방향을 이해하기 위한 비교 자료다. `accessibility_check.html`의 승인된 글자·조작 영역·간격과 `layout.css`의 `.a11y-*` 유효 크기는 축소 대상으로 제안하지 않는다.

## Computer Use로 점검하는 순서

1. **대상 확정:** 화면 목록, URL 또는 앱 창, 역할·테스트 계정, 화면별 기능 정의, 승인된 디자인 파일, 점검할 창 크기를 적는다. 소스 커밋과 실행 화면 버전도 맞춘다.
2. **창을 실제로 관찰:** `computer-use` 스킬의 `SKILL.md`를 읽고 대상 앱·창을 정확히 식별한다. 화면 상태를 관찰한 뒤 한 동작을 실행하고 다시 관찰한다. 접근 가능한 화면이 없으면 캡처나 확인 결과를 만들어 내지 않는다.
3. **같은 조건에서 비교:** 화면별 첫 화면과 아래쪽, 탭·필터·상세·접기·모달·빈 결과 상태를 본다. 데스크톱과 좁은 창을 비교할 때는 폭과 확대 상태를 기록한다.
4. **밀도·그리드 분석:** 제목 → 조건 → 결과 → 다음 행동이 첫 화면에서 이어지는지, 짧은 정보가 같은 줄에 묶이는지, 제목·필터·표·상세의 시작선과 열 간격이 일정한지 확인한다.
5. **증거 보고:** 화면명·상태·창 크기·캡처·관찰 결과를 남긴다. 화면에서 보이는 사실과 CSS/DOM 소스에서 측정한 값, 추정을 구분한다.

클릭으로 서버 데이터를 저장·삭제·전송하는 행동은 점검 범위에 넣지 않는다. 토글·탭·필터처럼 화면 상태만 바꾸는 조작도 결과를 재관찰한다.

## 촘촘함을 판단할 때 보는 항목

| 항목 | 충족되는 모습 | 재검토가 필요한 모습 |
|---|---|---|
| 정보 우선순위 | 관리자 화면은 업무명·조건·결과·처리 행동, 사용자 화면은 서비스 설명·신청 행동이 빠르게 보임 | 장식·반복 설명 때문에 핵심 행동이 첫 화면 아래로 밀림 |
| 밀도 | 짧은 조건·값을 가로로 묶고 반복 제목, 과한 카드 안쪽 여백, 빈 설명 영역을 덜어 냄 | 모든 항목을 큰 카드 한 개씩 세로로 쌓음 |
| 그리드 | 제목·필터·목록·상세가 공통 시작선을 따르고 같은 성격의 열 폭·간격이 예측 가능 | 섹션마다 시작선이 달라 시선이 계속 좌우로 이동 |
| 좌측 정렬 | 제목·본문·레이블·값·표 문자는 왼쪽에서 읽기 시작하고 상태·주요 행동은 정해진 위치에 둠 | 텍스트가 제각각 가운데·오른쪽으로 흩어짐 |
| 화면 유형 | 짧은 정보는 2~4단, 긴 설명·큰 표는 필요한 폭을 주고 목록+상세는 핵심 열을 유지 | 다단을 무조건 적용해 문장·표가 좁게 찢어지거나 중요한 열이 사라짐 |
| 간격과 경계 | 구분이 필요한 곳에만 선을 쓰고 제목·배경·레이블 굵기로 정보 묶음을 읽게 함 | 카드 안에 다시 카드와 테두리를 반복해 화면이 복잡해짐 |
| 읽기·조작 가능성 | 글자와 조작 영역을 유지한 채 정보 구조·여백을 정리함 | 촘촘함을 위해 글자·버튼·접근성 참고 화면의 크기를 먼저 줄임 |

**판정 방식:** 화면마다 `충족 / 일부 충족 / 미충족 / 확인 불가`를 쓰고, 각 항목에 실제 관찰 위치와 이유를 연결한다. 임의의 점수나 픽셀 수치를 지어내지 않는다. 필요하면 동일 창 크기에서 첫 화면에 보이는 필터·결과 행·상세 정보의 개수를 세어 비교한다.

## 화면 유형별로 꼭 볼 상태

| 화면 | 첫 화면에서 볼 것 | 상태 전환에서 볼 것 |
|---|---|---|
| 관리자 목록·상세 | 업무명·건수·상태·주요 버튼, 검색 조건, 목록 첫 행, 우측 상세의 시작선 | 필터 선택, 상세 열기·닫기, 빈 결과, 좁은 창의 핵심 열 유지 |
| 사용자·랜딩 | 서비스명과 핵심 설명, 신청 CTA, 대상·기간·방식 등 짧은 정보 묶음 | 탭·아코디언·모바일 순서, 긴 안내문 가독성 |
| 신청·입력 폼 | 짧은 필드의 적절한 열 배치, 긴 설명·메모의 전체 폭, 레이블 좌측 정렬 | 필수값 오류, 도움말, 제출 전 확인, 완료 상태 |

## 프롬프트 1. Computer Use로 전체 화면의 밀도·그리드 진단

**쓸 때:** 구현된 화면을 직접 확인받고 싶을 때. 아래의 `[대괄호]`를 실제 화면과 승인 기준으로 바꾼다. 화면 목록이 없다면 먼저 저장소·메뉴에서 목록을 작성한 뒤 점검한다.

```text
작업 모드: 점검 대상은 읽기·시각 관찰만. 디자인·소스·운영 데이터를 수정하지 마. 지정한 HTML 리포트 파일만 새로 작성해줘.
점검할 앱/브라우저 창과 URL: [정확한 이름·주소]
HTML 리포트 저장 경로: [예: reports/디자인_밀도_점검_리포트.html]
점검할 화면 목록과 사용자 역할: [관리자 목록, 회원 상세, 사용자 랜딩, 신청 폼 등]
비교 기준: [현행 디자인시스템 경로, 승인된 디자인/기능 문서, 밀도·그리드 UI 검토안]
실행 소스 버전: [커밋/빌드 버전 또는 확인 필요]
창 크기·확대 조건: [데스크톱 폭, 좁은 창 폭, 확대 상태]
보호 대상: accessibility_check.html과 layout.css의 .a11y-* 승인 크기, 실제 사용자 데이터

1. 사용 가능한 computer-use 스킬을 확인하고 SKILL.md 지침을 읽어줘. 대상 앱과 창을 실제 목록에서 정확히 선택한 뒤 화면 상태를 관찰해줘. 사용할 수 없으면 그 이유와 미검증 범위를 적고 화면을 봤다고 주장하지 마.
2. 먼저 화면별 점검 목록을 만들어줘. 각 화면의 목적, 핵심 정보, 최초 상태, 눌러볼 UI 상태(탭·필터·접기·상세·빈 결과·오류)를 정리해줘.
3. 각 화면을 같은 창 크기에서 열어 첫 화면과 필요한 아래쪽을 캡처하고, 가능한 상태 전환을 한 번씩 관찰해줘. 클릭 후에는 변경된 상태를 다시 확인해줘. 실제 저장·삭제·제출은 하지 마.
4. 제목 → 조건 → 결과 → 다음 행동이 첫 화면에서 이어지는지, 반복 제목·큰 카드 여백·불필요한 줄바꿈 때문에 정보가 밀려나지 않는지 확인해줘.
5. 제목·본문·레이블·값·필터·표·상세의 왼쪽 시작선과 열 간격을 비교해줘. UI 검토안의 '정렬선 보기'와 '제안: 촘촘하게 / 비교: 넓게'는 구조 비교에 활용하되 가상 데이터는 실서비스 데이터로 옮기지 마.
6. 관리자 화면은 검색 조건과 목록·상세의 동시 비교, 사용자·랜딩은 핵심 설명과 신청 행동, 폼은 짧은 필드와 긴 설명의 폭 배치를 각각 확인해줘.
7. 데스크톱과 좁은 창에서 겹침·잘림·가로 스크롤과 핵심 정보 누락을 확인해줘. 창 크기를 바꿀 수 없다면 해당 상태를 미검증으로 적어줘.
8. 촘촘함을 위해 글자·버튼·접근성 참고 화면의 승인 크기를 줄이는 제안은 하지 마. 정보 묶음, 반복 문구, padding, gap, 불필요한 경계부터 검토해줘.
9. 화면에서 관찰한 사실, 소스에서 확인한 수치, 추정을 구분하고, 원본 데이터나 디자인을 임의로 바꾸지 않는 수정 방향만 제안해줘.

결과 표: 화면·상태 | 창 크기·캡처 근거 | 기대 구조 | 실제 관찰 |
밀도(충족/일부/미충족/확인 불가) | 그리드·좌측 정렬 | 첫 화면 핵심 정보 |
사용성 영향 | 수정 우선순위 | 구체적 수정 방향 | 재확인 방법.
끝에 화면별 판정과 공통 컴포넌트에서 반복되는 문제, 확인하지 못한 화면·상태를 요약해줘.
위 결과를 지정한 경로에 단독으로 열 수 있는 한국어 HTML 리포트로 저장해줘. 상단에는 점검일·대상 버전·기준 문서·창 크기·화면 수와 전체 판정 요약을 넣어줘. 화면별로 첫 화면과 상태 전환 캡처(있을 때만), 기준/실제 비교, 밀도·그리드·좌측 정렬·좁은 창 판정, 눈에 보이는 증거, 우선 수정안을 보여줘. 캡처에는 설명과 파일 링크를 붙이고 실제 사용자 개인정보는 가려줘. 인쇄와 좁은 화면에서도 읽히게 하고, 외부 CDN 없이 열리게 해줘. 관찰하지 못한 화면은 '확인 불가'로 남겨줘. 마지막 답변에는 HTML 파일 경로와 가장 큰 차이 3가지만 알려줘.
```

## HTML 리포트에서 확인할 것

| 영역 | 반드시 남길 내용 |
|---|---|
| 표지·범위 | 점검일, 앱/URL, 소스 버전, 승인 기준, 역할, 창 크기·확대 상태, 화면 목록 |
| 한눈에 보기 | 화면별 `충족/일부 충족/미충족/확인 불가`와 공통으로 반복되는 문제 |
| 화면별 비교 | 동일 조건의 화면 캡처, 첫 화면 정보량, 시작선·열 간격·좌측 정렬, 빈 공간·중첩 경계, 좁은 창 상태 |
| 수정·재검증 | 반복 컴포넌트와 화면별 우선순위, 정보 묶음·여백 조정 제안, 같은 조건에서 다시 볼 항목 |
| 미검증 | 열지 못한 화면·상태, 캡처가 없는 항목, 소스에서만 추정한 수치 |

캡처는 화면과 상태를 식별할 수 있게 제목·대체 설명을 붙인다. `확인 불가`를 `충족`으로 계산하지 않고, 임의의 점수·픽셀 수치·전후 이미지를 만들지 않는다.

## 프롬프트 2. 수정 후 화면별 재검증

```text
작업 모드: 점검 대상은 읽기·시각 관찰만. 배포나 운영 데이터 변경을 하지 마. 지정한 HTML 재검증 리포트만 새로 작성해줘.
이전 진단 결과: [보고서 경로]
수정 전/후 소스 버전과 화면 URL: [각각 정확히]
비교할 화면·상태·창 크기: [이전 점검과 동일한 목록]
HTML 재검증 리포트 저장 경로: [예: reports/디자인_밀도_재검증_리포트.html]

computer-use 스킬이 사용 가능하면 이전과 같은 화면·상태·창 크기로 다시 관찰해줘.
```
