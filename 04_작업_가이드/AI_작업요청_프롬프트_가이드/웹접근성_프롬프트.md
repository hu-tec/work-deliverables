# 웹접근성: 반복 원인 설명과 점검·수정 프롬프트

**이 탭의 용도:** 웹접근성 이슈가 왜 반복되는지 팀에 설명하고, 실제 화면을 근거로 점검·수정·재검증을 요청할 때 사용한다. `[대괄호]`를 현재 프로젝트 정보로 바꾼다.

## 점검 전에 확인할 기준

국내 웹 화면은 KWCAG 2.2의 실제 검사항목을 기준으로 확인하고, 운영 주체에 따른 법적 의무와 품질인증은 구분한다. 자세한 법령·표준 설명은 [10번 법령·기준](../../index.html#legal-accessibility)에 정리했다.

## 프롬프트 1. 웹접근성 관련 법령 적용 범위 조사

```text
작업 모드: 읽기만. 사이트·코드를 수정하지 마.
운영 주체: [공공기관/민간사업자/교육기관/협회 등 정확한 법적 주체]
대상 서비스: [웹사이트 URL, 모바일 앱 여부, 회원·신청·결제·증명서 흐름]
적용 판단일: [YYYY-MM-DD]

국가법령정보센터의 해당 날짜 시행 법령을 기준으로 다음을 분리해서 조사해줘:
1. 장애인차별금지법 제21조와 시행령 제14조·별표의 적용 대상과 필요한 편의
2. 디지털포용법 제19조의 국가기관등 의무와 지능정보사업자 규정 중 해당되는 부분
3. KWCAG 2.2를 기술 점검 기준으로 사용할 항목과 별도 품질인증 제도
4. 구 지능정보화 기본법 제46·47조를 현행 근거로 잘못 인용한 자료가 있는지

결과 표: 법령/기준 | 시행일 | 적용 대상 | 이 서비스 해당 여부와 근거 | 확인할 화면·기능 | 담당자 결정 필요.
운영 주체나 서비스 범위가 확인되지 않으면 적용을 단정하지 말고 필요한 자료를 적어줘.
기술적 결함, 법적 의무, 인증 취득 여부를 서로 다른 결론으로 보고해줘.
```

## 프롬프트 2. KWCAG 기준을 팀에 쉽게 설명받기

```text
작업 모드: 읽기만. 파일을 수정하지 마.
대상 서비스와 화면: [정확한 이름·URL]
설명 대상: [기획자/디자이너/개발자/경영진]
기준 문서: 국립전파연구원 '한국형 웹 콘텐츠 접근성 지침 2.2'(KS X OT0003)

KWCAG가 무엇이고 WCAG와 어떤 관계인지 공식 기준을 근거로 설명해줘.
인식·운용·이해·견고성 네 원칙마다 이 서비스의 화면에서 볼 수 있는 예시를 2개씩 들어줘.
예시마다 '해당 기능 → 사용자가 겪는 문제 → 확인 방법 → 관련 KWCAG 검사항목'을 연결해줘.
2022년 2.2 개정에서 추가된 항목 중 이 서비스와 관련 있는 것도 표준 원문과 대조해줘.
KWCAG·WCAG의 검사항목 번호를 섞지 말고, 법적 적용 여부와 품질인증은 별도 판단 항목으로 표시해줘.
완료물: 비전문가용 1분 설명, 역할별 확인 목록, 실제 화면 근거가 없는 예시는 '가상 예시' 표시.
```

## 웹접근성 이슈가 자주 발생하는 이유

접근성은 화면의 색상이나 HTML 속성 몇 개로 끝나지 않는다. 사용자가 **읽고 → 조작하고 → 결과를 확인하는 전체 흐름**에서 작동해야 한다. 기능·콘텐츠·디자인이 바뀔 때 다음 지점이 함께 점검되지 않으면 같은 문제가 반복된다.

| 반복 원인 | 화면에서 나타나는 현상 | 점검할 질문 |
|---|---|---|
| 마우스 클릭만 기준으로 개발 | 탭·메뉴·대화상자를 키보드로 열거나 닫을 수 없음 | Tab·Shift+Tab·Enter·Space·Esc로 끝까지 사용할 수 있는가? |
| 시각적 모양과 의미 구조가 다름 | 제목처럼 보이는 글이 일반 `div`, 버튼처럼 보이는 요소가 클릭 가능한 `span` | 제목·링크·버튼·폼에 실제 의미가 있는 요소를 썼는가? |
| 기본 화면만 검수 | 검색 결과 없음, 입력 오류, 로딩, 팝업, 펼침 상태에서 안내와 초점 이동이 누락 | 모든 상태에서 무엇이 바뀌었는지 알 수 있는가? |
| 컴포넌트와 콘텐츠가 따로 변경 | 공통 탭 하나의 결함이 여러 화면으로 퍼짐, 이미지 대체 텍스트 누락 | 공통 컴포넌트와 콘텐츠 등록 절차에 검수 기준이 있는가? |
| 디자인 변경 뒤 재검증 누락 | 대비·초점 표시·확대 시 잘림·터치 대상이 회귀 | 변경 전후 동일한 사용자 흐름을 다시 확인했는가? |
| 자동 검사 결과만 신뢰 | 스캔은 통과했지만 읽는 순서·대체 텍스트의 적절성·실제 조작이 불편 | 자동 검사와 사람의 키보드·보조기술 점검을 구분했는가? |

W3C는 개발·재설계 과정에서 **일찍, 반복해서** 평가하고, 자동 도구만으로 접근성 기준 충족 여부를 판단할 수 없다고 안내한다. 국내 기준 점검에도 실제 사용자 흐름을 조작해 확인하는 과정이 필요하다. [W3C 평가 안내](https://www.w3.org/WAI/test-evaluate/)

이 저장소의 `01_화면_디자인/디자인시스템/accessibility_check.html`은 승인된 접근성 참고 화면이다. 해당 화면의 글자·컨트롤·간격·배치 크기와 `layout.css`의 `.a11y-*` 유효 크기는 저장소의 `AGENTS.md`에 따라 보호한다.

## 프롬프트 3. 왜 반복되는지 비전문가에게 설명받기

**쓸 때:** 팀·고객에게 원인을 설명해야 하지만 아직 코드를 수정할 단계는 아닐 때.

```text
작업 모드: 읽기만. 파일을 수정하지 마.
대상: [사이트 URL 또는 로컬 화면 경로]
사용자 흐름: [예: 메뉴 이동 → 신청 폼 입력 → 오류 확인 → 제출]
최근 변경: [기능·디자인·콘텐츠 변경 내역 또는 확인 필요]

이 화면에서 웹접근성 이슈가 반복되는 이유를 실제 코드와 화면 상태를 근거로 설명해줘.
1. 키보드 조작, 의미 구조, 화면 읽기 순서, 대체 텍스트, 폼 안내·오류, 색 대비·확대, 동적 상태 안내로 나눠 확인해줘.
2. 각 원인에 대해 '사용자가 겪는 불편 → 재현 순서 → 관련 파일/요소 → 반복되는 개발 과정상의 이유'를 연결해줘.
3. 직접 확인하지 않은 원인을 사실처럼 쓰지 말고 '가능성/확인 필요'로 표시해줘.
4. 비개발자에게 설명하는 5문장 요약과 개발팀용 상세 표를 모두 작성해줘.
5. 자동 검사 결과와 직접 키보드·보조기술로 확인한 결과를 구분해줘.
6. 국내 점검 기준은 KWCAG 2.2(KS X OT0003)로 두고, 관련 검사항목 명칭·번호를 실제 표준에서 확인해줘.
   WCAG 2.2를 함께 언급할 때는 별도 참고 기준으로 표시하고 번호를 혼용하지 마.
7. 수정 우선순위는 이용 불가, 작업 완료 방해, 이해 저하 순으로 제안해줘.
완료물: 재현 근거가 있는 문제 목록, 원인 설명, 재발 방지 점검 지점. 구현·커밋은 하지 마.
```

## 프롬프트 4. 화면·상태별 접근성 점검

**쓸 때:** 어디가 문제인지 먼저 정확히 확인할 때. WCAG 번호는 실제 해당하는 기준만 적게 한다.

```text
작업 모드: 읽기만. 파일을 수정하지 마.
대상 화면: [정확한 URL/파일 경로]
점검 범위: [예: 상단 메뉴, 검색, 결과 표, 상세 대화상자, 신청 폼]
우선 기준: KWCAG 2.2(KS X OT0003). 적용할 검사항목은 공식 표준에서 확인
추가 참고: WCAG 2.2 [필요한 경우만 별도로 비교]
보호: 원본 데이터·문구·기존 디자인·접근성 참고 화면의 승인된 크기

다음 상태를 실제로 열어 확인해줘: 기본, 키보드 초점, 펼침/선택, 입력 오류, 결과 없음, 로딩/완료, 모바일 폭, 확대.
각 상태에서 제목·랜드마크, 이미지 대체 텍스트, 폼 라벨·오류 연결, 키보드 순서·초점 표시·초점 복귀,
상태 변화 알림, 색상 외 정보 표현, 확대 시 가림·가로 스크롤을 점검해줘.

결과 표 열: 화면/상태 | 재현 순서 | 기대 동작 | 실제 동작 | 사용자 영향 | KWCAG 검사항목·근거 | WCAG 추가 참고(해당 시) | 코드 위치 | 수정 제안 | 검증 방법.
KWCAG와 WCAG의 번호가 같다고 가정하지 말고 각각 원문을 확인해줘.
확인하지 못한 상태는 '미검증'으로 표시하고 필요한 테스트 환경을 적어줘.
자동 점검만으로 '웹접근성 준수 완료'라고 결론 내리지 마.
```

## 프롬프트 5. 승인된 디자인을 유지하며 결함 수정

**쓸 때:** 재현 가능한 문제와 변경 범위가 확정된 뒤.

```text
작업 모드: 범위 내 구현
문제: [점검표의 정확한 항목/재현 순서]
수정 허용 파일: [정확한 경로]
보호 파일·값: [원본 데이터/콘텐츠/디자인 기준과 변경 금지 파일]
완료 기준: [키보드·화면 읽기·오류 안내에서 기대하는 구체적 결과]

먼저 원인 코드와 관련 컴포넌트를 찾아 변경 계획을 짧게 써줘.
필요한 의미 요소, 이름/설명 연결, 키보드 조작, 초점 이동·복귀, 변경 상태 안내만 수정해줘.
디자인을 임의로 다시 만들지 말고, 시각적 변경이 필요한 경우 바뀌는 위치와 이유를 명시해줘.
공통 컴포넌트라면 영향을 받는 다른 화면도 확인해줘.
이 저장소의 accessibility_check.html 및 layout.css의 .a11y-* 승인 크기는 변경하지 마.

검증: 마우스 없이 전체 흐름 완료, Tab/Shift+Tab/Enter/Space/Esc, 오류·빈 결과·완료 상태,
화면 확대와 좁은 너비, 가능한 경우 실제 화면 읽기 도구로 이름·상태·순서를 확인해줘.
보고: 변경 파일, 전후 사용자 동작, 실제 수행한 검증, 미검증 사항을 구분해줘.
```

## 프롬프트 6. 다음 배포에서 같은 문제가 다시 생기지 않게 하기

```text
작업 모드: 검토·제안만. 현재 제품 파일은 수정하지 마.
대상: [반복 문제가 생긴 공통 컴포넌트/화면]
최근 접근성 이슈: [재현 가능한 사례 2~3개]

이슈별로 설계·개발·콘텐츠 등록·코드 리뷰·배포 검수 중 어느 단계에서 놓쳤는지 근거를 찾아줘.
각 단계에서 실행할 수 있는 짧은 점검 항목을 만들고 담당 역할을 제안해줘.
자동 검사로 잡히는 항목과 사람이 조작해야 확인되는 항목을 분리해줘.
완료물: 공통 컴포넌트 점검표, 화면 상태별 검수표, 배포 전 필수 재현 시나리오.
```

## 개발 소스를 받았을 때의 접근성 검토 순서

납품된 소스에서 `alt`나 `aria-*` 문자열만 검색해서는 사용 가능 여부를 알 수 없다. **어떤 버전을 받았는지 확인 → 빌드·실행 → 화면과 코드 연결 → 자동 검사 → 키보드·보조기술로 실제 흐름 조작 → 결함 재현과 재검증** 순서로 검토한다. 실행할 수 없다면 그 이유와 필요한 환경을 남기고, 코드 검토만으로 적합 판정을 하지 않는다.

| 단계 | 확인할 증거 | 빠지기 쉬운 부분 |
|---|---|---|
| 인수물 확정 | Git 커밋/태그, 빌드 방법, 의존성 잠금 파일, 테스트 URL, 화면·기능 목록 | 제출된 소스와 시연 화면이 다른 버전 |
| 범위 매핑 | 페이지·공통 컴포넌트·동적 상태·문서 다운로드의 파일 위치 | 공통 컴포넌트 하나의 결함이 여러 화면에 전파 |
| 정적·자동 점검 | 의미 요소, 레이블·대체 텍스트, 자동 도구 결과와 실행 환경 | 도구가 통과해도 실제 읽기 순서·문구 적절성은 미확인 |
| 사람의 사용 흐름 | 키보드만으로 시작부터 완료까지 조작, 초점 표시·복귀, 화면 읽기 도구의 이름·상태 안내 | 오류·빈 결과·팝업·완료처럼 초기 화면 밖의 상태 |
| 결과 보고 | KWCAG 검사항목, 재현 순서, 코드 위치, 사용자 영향, 수정·재검증 방법 | 추정과 실제 재현을 섞어 ‘적합’이라고 보고 |

## 점검 수단 선택

브라우저 자동화 스킬은 흐름 재현을 도울 수 있지만 KWCAG 적합성 판정은 수동 검수도 필요하다. 설치 상태와 사용법은 [11번 점검 스킬·도구](../../index.html#skill-accessibility)를 참고한다.

## 프롬프트 7. 납품된 개발 소스의 KWCAG 인수 검토

```text
작업 모드: 점검 대상은 읽기만. 납품 소스·원본 데이터·디자인을 수정하지 마. HTML 리포트 파일만 새로 작성해줘.
소스 위치와 버전: [압축 해제 경로 또는 Git 저장소·커밋/태그]
HTML 리포트 저장 경로: [예: reports/웹접근성_인수_리포트.html]
빌드·실행 설명서: [문서 경로]
테스트 환경/URL: [주소 또는 없음]
검토할 사용자 흐름: [예: 로그인 → 신청 → 입력 오류 → 제출 → 증명서 다운로드]
화면·기능 정의와 디자인 기준: [정확한 문서/파일]
우선 기술 기준: KWCAG 2.2(KS X OT0003)

1. 받은 파일·버전·의존성·실행 방법을 확인하고, 실행한 화면이 제출 소스에서 나온 것인지 밝혀줘.
2. 화면/컴포넌트/상태/다운로드 문서를 코드 파일과 매핑해줘. 범위 밖은 별도로 표시해줘.
3. 정적 분석과 자동 접근성 검사 결과를 기록하되, 도구가 확인하지 못하는 항목은 사람의 검사로 남겨줘.
   사용 가능한 점검 스킬을 먼저 확인하고, Playwright 스킬이 활성화되어 있으면 그 절차로 사용자 흐름을 재현해줘. 미설치라면 사용했다고 주장하지 마.
4. 키보드만으로 전체 흐름을 조작하고 초점 순서·표시·복귀, 팝업·탭·아코디언·폼 오류·완료 상태를 확인해줘.
5. 화면 읽기 도구를 사용할 수 있으면 이름·역할·상태·읽기 순서를 확인하고 도구/환경을 적어줘.
6. 좁은 화면과 확대 상태에서 가림·겹침·가로 스크롤, 색 외 정보 전달, 대체 텍스트를 확인해줘.
7. 결함마다 공식 KWCAG 검사항목의 정확한 이름·번호를 원문과 대조해줘. WCAG 번호와 섞지 마.
8. 접근성 참고 화면 accessibility_check.html과 layout.css의 .a11y-* 승인 크기는 변경 대상으로 제안하지 마.

결과 표: 화면/상태 | 실제 재현 순서 | 기대/실제 | 사용자 영향 | KWCAG 항목 |
소스 파일·위치 | 확인 방식(실행/자동/코드 추정) | 심각도 | 수정 제안 | 재검증 방법.
끝에 인수 판단을 '확인된 결함 없음/조건부 보완/핵심 흐름 사용 불가/판단 보류'로 제안하고 근거를 적어줘.
실행하지 못한 검사와 법적·인증 판단은 '미검증'으로 남겨줘.
결과를 지정한 한국어 HTML 파일로 저장해줘. 대상 버전·점검일·환경·사용 도구, 화면/상태별 범위, 결함의 KWCAG 근거·재현·증거·수정·재검증 방법, 미검증 항목을 포함하고 좁은 화면·인쇄에서 읽히게 해줘. 실제 개인정보나 없는 캡처를 넣지 마. 마지막 답변에는 리포트 경로와 핵심 발견만 알려줘.
```
