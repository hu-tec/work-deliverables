# PDF만으로 기능정의가 누락되는 이유

작성일: 2026-05-28  
작성 목적: Figma/PDF 화면 자료만 분석했을 때 시험 플랫폼의 기능정의가 누락되는 원인을 정리하고, 이후 분석 보완 기준을 세우기 위함

## 1. 한 줄 요약

PDF는 화면의 “겉모습”을 전달하는 자료이지, 서비스의 “업무 규칙”과 “상태 흐름”을 완전히 담는 자료가 아니다.  
따라서 PDF만 보고 기능정의를 만들면 화면에 보이는 버튼, 탭, 입력칸은 추출할 수 있지만, 실제 개발에 필요한 조건, 예외, 권한, 데이터 상태, 관리자 처리 절차가 빠지기 쉽다.

이번 프로젝트에서도 수험생 화면은 `접수 → 결제 → 응시 → 결과 → 자격증 신청`처럼 사용자의 흐름이 비교적 명확해서 먼저 구현할 수 있었다. 반면 출제자 영역의 `시험 출제하기`, `출제 내역`, `전문가 프로필`은 화면명은 보이지만 세부 업무 규칙이 부족해 실제 기능 개발 기준이 불명확했다.

## 2. 왜 PDF 분석에서 누락이 발생하는가

### 2.1 PDF는 정적인 화면 캡처다

PDF는 특정 순간의 화면을 보여준다. 하지만 실제 서비스 기능은 여러 상태를 오가며 동작한다.

예를 들어 `시험 출제하기` 화면이 PDF에 있어도 다음 정보는 PDF 한 장만으로 확정하기 어렵다.

| 필요한 정보 | PDF만으로 부족한 이유 |
|---|---|
| 임시저장 가능 여부 | 버튼이 없거나 일부 화면에만 있으면 정책을 알 수 없다. |
| 제출 후 수정 가능 여부 | 제출 전/후 상태 화면이 따로 없으면 판단하기 어렵다. |
| 관리자 승인 절차 | 승인자, 승인 기준, 반려 사유 입력 방식이 화면에 드러나지 않을 수 있다. |
| 필수 입력값 | 빨간 별표가 있어도 실제 검증 규칙까지 알 수 없다. |
| 문항 수 제한 | 화면에는 입력 영역만 보이고 시험별 제한은 별도 정책일 수 있다. |

즉, PDF는 “보이는 화면”은 설명하지만 “동작하는 업무”를 충분히 설명하지 않는다.

### 2.2 화면명과 메뉴명은 기능정의가 아니다

PDF나 Figma에서 `출제 내역`, `전문가 프로필`, `1:1 문의` 같은 메뉴명이 보이면 기능이 존재한다는 힌트는 된다. 하지만 개발에 필요한 기능정의는 더 구체적이어야 한다.

예를 들어 `출제 내역`이라는 메뉴명만으로는 다음을 알 수 없다.

| 개발에 필요한 질문 | 예시 |
|---|---|
| 어떤 목록을 보여주는가? | 내가 작성한 문항, 내가 배정받은 시험, 제출한 출제안 중 무엇인가? |
| 상태값은 무엇인가? | 임시저장, 제출, 검토중, 반려, 승인, 게시완료 등 |
| 사용자가 할 수 있는 작업은 무엇인가? | 수정, 삭제, 복사, 재제출, 철회, 다운로드 |
| 누가 볼 수 있는가? | 본인만, 같은 기관 전문가, 관리자 전체 |
| 검색/필터 기준은 무엇인가? | 시험명, 급수, 분야, 상태, 기간 |

메뉴명은 IA의 일부이고, 기능정의는 업무 규칙과 데이터 흐름까지 포함해야 한다.

### 2.3 화면에 없는 상태가 실제로는 더 많다

실제 시험 플랫폼은 상태 기반 시스템이다. 접수, 결제, 응시, 채점, 결과, 자격증, 문의, 출제, 승인까지 모두 상태 전이가 있다.

PDF에는 보통 대표 상태만 담긴다. 그러나 개발에서는 “안 되었을 때”가 더 중요하다.

| 영역 | 화면에 잘 보이는 상태 | 누락되기 쉬운 상태 |
|---|---|---|
| 시험 접수 | 접수하기, 접수 완료 | 접수 전, 마감, 정원 초과, 중복 접수, 접수 취소 |
| 결제 | 결제하기, 결제 완료 | 결제 실패, 결제대기, 환불신청, 환불완료 |
| 시험 응시 | 응시 시작, 제출 | 결제 전 응시 불가, 기간 전/후 응시 불가, 이미 제출, 미응시 |
| 결과 | 합격, 불합격 | 채점중, 결과 보류, 이의신청, 재채점 |
| 자격증 | 신청하기, 발급완료 | 신청대상 아님, 발급중, 반려, 재발급 |
| 출제 | 출제 작성 | 임시저장, 제출, 반려, 수정요청, 승인, 게시 |

PDF만 분석하면 대표 상태 중심으로 기능이 정의되고, 예외 상태나 실패 상태가 빠질 가능성이 높다.

### 2.4 권한과 역할 간 연결이 화면만으로는 불명확하다

시험 플랫폼에는 최소한 다음 역할이 있다.

| 역할 | 주요 업무 |
|---|---|
| 수험생 | 시험 접수, 결제, 응시, 결과 확인, 자격증 신청, 문의 |
| 출제자/전문가 | 문제 출제, 제출, 반려 수정, 프로필 관리 |
| 채점자 | 답안 채점, 피드백 작성, 채점 이력 관리 |
| 관리자 | 회원, 시험, 문제, 채점, 결제, 자격증, 문의, 통계 관리 |

PDF가 역할별로 완전하게 묶여 있지 않으면, 어떤 화면을 누가 쓰는지 혼동된다.  
특히 2025 자료처럼 사용자 UX 참고 화면, 전문가 화면, 관리자 화면이 섞여 있으면 “구현 대상 기능”과 “참고용 UI”를 구분하기 어렵다.

예를 들어 `창작작업실`, `메타-T 번역`, `장바구니`, `결제` 화면은 시험 플랫폼 본류 기능인지, AI 작업 서비스 참고 화면인지 판단이 필요하다. 이 판단 없이 기능정의를 만들면 시험 플랫폼에 필요 없는 기능이 들어가거나, 반대로 필요한 시험 기능이 뒤로 밀릴 수 있다.

### 2.5 데이터 구조가 보이지 않는다

개발은 화면보다 데이터 구조에 더 크게 영향을 받는다. PDF에는 보통 데이터 테이블의 일부 컬럼만 보이거나, 예시 값만 들어 있다.

하지만 구현에는 다음이 필요하다.

| 필요한 데이터 정의 | 예시 |
|---|---|
| 시험 기본 데이터 | 시험종목, 급수, 분야, 회차, 지역, 응시료, 정원, 접수기간, 시험일 |
| 접수 데이터 | 접수번호, 수험생, 시험, 결제상태, 취소/환불상태 |
| 응시 데이터 | 시험 시작시간, 제출시간, 답안, 미응시 여부 |
| 출제 데이터 | 출제자, 문항, 모범답안, 채점기준, 상태, 반려 사유 |
| 채점 데이터 | 채점자, 점수, 피드백, 승인 여부 |
| 자격증 데이터 | 자격번호, 신청상태, 발급상태, 검증코드 |

PDF에서 컬럼명이 일부 보이더라도 관계형 구조, 필수값, 상태값, 고유번호, 이력 저장 방식은 별도로 정의해야 한다.

### 2.6 입력 폼의 검증 규칙이 빠진다

PDF에는 입력칸이 보인다. 하지만 입력값의 규칙은 보통 보이지 않는다.

예를 들어 전문가 프로필 화면에 `학력`, `경력`, `저서`, `해외거주 경험` 입력 영역이 보여도 다음은 별도 정의가 필요하다.

| 항목 | 추가로 필요한 규칙 |
|---|---|
| 학력 | 여러 개 입력 가능한지, 졸업/수료 상태가 있는지 |
| 경력 | 기간 중복 허용 여부, 증빙 파일 필요 여부 |
| 전문 분야 | 시험 분류와 연결되는지, 복수 선택 가능한지 |
| 정산 정보 | 계좌번호 저장 여부, 관리자 승인 여부 |
| 프로필 공개 | 수험생에게 노출되는지, 관리자만 보는지 |

화면은 입력칸의 존재만 보여주고, 입력값의 검증과 승인 정책은 별도 업무 정의가 필요하다.

### 2.7 PDF 추출 품질의 한계가 있다

PDF 분석은 파일 상태와 도구의 영향을 많이 받는다.

| 문제 | 영향 |
|---|---|
| 텍스트가 이미지로 박혀 있음 | OCR 없이 정확한 문구 추출이 어렵다. |
| 화면 일부만 잘려 있음 | 하단 버튼, 우측 컬럼, 팝업이 누락될 수 있다. |
| 여러 상태가 한 PDF에 겹쳐 있음 | 실제 화면 흐름을 오해할 수 있다. |
| 파일명이 일반적임 | `구분-1.pdf`, `제목 없음.pdf` 같은 이름은 의미 추론이 어렵다. |
| Figma 컴포넌트 정보가 없음 | 클릭 연결, variants, hidden layer, prototype flow를 볼 수 없다. |

따라서 PDF만으로 만든 기능정의는 “가설”에 가깝고, 개발 기준으로 쓰려면 검증 단계가 필요하다.

### 2.8 원본 Figma 레이어와 프레임 구조가 기능 단위로 정리되지 않았을 수 있다

PDF 누락의 원인은 PDF 자체의 한계뿐 아니라, 원본 Figma 파일의 정리 방식에서도 발생할 수 있다.  
Figma에서 화면, 기능, 상태, 컴포넌트가 업무 단위로 묶여 있지 않으면 PDF로 내보냈을 때 기능 관계가 더 약해진다.

특히 다음 경우에는 기능정의 누락 가능성이 높다.

| Figma 정리 문제 | 기능정의에 미치는 영향 |
|---|---|
| 버튼, 입력창, 안내문구가 각각 흩어진 레이어로 존재 | 하나의 기능 흐름으로 인식하기 어렵다. |
| 프레임명이 `Frame 123`, `Group 45`, `Rectangle`처럼 의미 없음 | 화면 목적과 업무 단위를 추론하기 어렵다. |
| 모달, 토스트, 에러, 빈 상태가 별도 상태로 분리되지 않음 | 예외/실패 케이스가 기능정의에서 빠질 수 있다. |
| 사용자 흐름이나 prototype 연결이 없음 | 버튼 클릭 후 이동, 승인 흐름, 상태 전이를 알기 어렵다. |
| 역할별 화면이 섞여 있음 | 수험생, 출제자, 관리자 기능 범위가 혼동된다. |
| 컴포넌트 variant, hidden layer, section 구분이 정리되지 않음 | 조건별 UI와 실제 기능 차이를 놓칠 수 있다. |

즉, PDF는 “보이는 화면”만 남기기 때문에 Figma 내부 구조가 정리되어 있지 않을수록 기능 단위 추론이 더 어려워진다.  
따라서 기능정의 누락은 PDF 변환 과정의 문제이면서, 원본 Figma의 정보 구조 부족 문제이기도 하다.

## 3. 이번 프로젝트에서 실제로 보인 증상

현재 구현 상태를 기준으로 보면 다음 차이가 있다.

| 영역 | 현재 판단 |
|---|---|
| 수험생 | 접수, 결제, 응시, 결과, 자격증, 1:1 문의, 내 정보까지 데모 흐름 구현 가능 |
| 출제자 | 홈 화면은 가능하지만 시험 출제하기, 출제 내역, 전문가 프로필은 상세 규칙 부족 |
| 채점자 | 채점 화면 메뉴는 있으나 배정 방식, 채점 기준, 피드백 규칙 부족 |
| 관리자 | 대시보드와 큰 메뉴는 보이나 CRUD 기준, 승인/반려/일괄처리 정책 부족 |

즉, PDF 분석 결과는 “사이트맵 초안”으로는 쓸 수 있지만, “개발 가능한 기능정의서”로는 밀도가 부족하다.

## 4. 기능정의 누락을 줄이는 보완 방법

### 4.1 화면별로 질문표를 만들어야 한다

각 메뉴마다 다음 질문에 답해야 한다.

| 질문 | 확인 내용 |
|---|---|
| 누가 쓰는가? | 수험생, 출제자, 채점자, 관리자 |
| 무엇을 생성/조회/수정/삭제하는가? | CRUD 대상 |
| 상태값은 무엇인가? | 접수중, 결제완료, 제출, 승인 등 |
| 다음 단계는 무엇인가? | 버튼 클릭 후 이동/상태 변경 |
| 안 되는 조건은 무엇인가? | 권한 없음, 기간 종료, 중복, 필수값 누락 |
| 관리자 개입이 있는가? | 승인, 반려, 강제 변경, 답변 |
| 데이터는 어디에 저장되는가? | 테이블/엔티티/필드 |
| 알림이 필요한가? | 이메일, SMS, 카카오, 내부 알림 |

### 4.2 역할별 플로우를 먼저 확정해야 한다

화면 단위가 아니라 역할별 업무 흐름으로 정리해야 한다.

예시:

```text
출제자
전문가 프로필 등록 → 관리자 승인 → 출제 가능 시험 확인 → 문항 작성 → 임시저장
→ 제출 → 관리자/검수자 검토 → 반려 수정 또는 승인 → 출제 내역 확정
```

이 흐름이 있어야 각 화면에 필요한 버튼, 상태, 권한이 자연스럽게 결정된다.

### 4.3 “되었을 때”와 “안 되었을 때”를 같이 정의해야 한다

개발 기준으로는 성공 케이스만 있으면 부족하다.

예를 들어 시험 응시는 다음처럼 나눠야 한다.

| 케이스 | 처리 |
|---|---|
| 결제 완료 + 시험 전 | 응시 가능 |
| 결제대기 | 결제 화면으로 안내 |
| 접수 취소 | 응시 불가 |
| 이미 제출 | 결과 화면으로 안내 |
| 문항 미연결 | 응시 시작 비활성화 |
| 시험기간 종료 | 응시 불가, 문의 안내 |

이 기준이 있어야 사용자가 막혔을 때도 화면이 제대로 동작한다.

### 4.4 Figma 원본은 기능 단위로 다시 정리해야 한다

PDF 분석을 보완하려면 원본 Figma에서 화면을 단순 시각 자료가 아니라 기능 분석 가능한 구조로 정리해야 한다.

| 정리 기준 | 목적 |
|---|---|
| 화면별 최상위 프레임명 명확화 | 화면 목적과 역할을 바로 알 수 있게 한다. |
| 역할별 섹션 분리 | 수험생, 출제자, 채점자, 관리자 기능을 구분한다. |
| 기능 단위 그룹화 | 버튼, 입력값, 안내문구, 결과 상태를 하나의 업무 단위로 묶는다. |
| 상태 화면 분리 | 기본, 로딩, 빈 데이터, 오류, 권한 없음, 완료 상태를 확인한다. |
| 모달/토스트/알림 별도 명명 | 화면에 잠깐 나타나는 기능을 누락하지 않는다. |
| prototype 연결 또는 흐름 주석 추가 | 클릭 후 이동, 상태 변경, 승인 절차를 추적한다. |
| 컴포넌트와 variant 이름 정리 | 조건별 UI 차이를 기능 규칙으로 연결한다. |

이 정리가 되어 있으면 PDF로 보이지 않는 정보도 Figma 원본에서 확인할 수 있고, 화면 단위가 아니라 기능 단위로 정의서를 보완할 수 있다.

### 4.5 PDF 분석 결과는 확정 문서가 아니라 초안으로 다뤄야 한다

PDF에서 뽑은 내용은 다음처럼 등급을 나눠야 한다.

| 등급 | 의미 | 개발 가능 여부 |
|---|---|---|
| 확정 | 화면, 데이터, 상태, 권한이 모두 명확함 | 바로 구현 가능 |
| 추정 | 화면은 있으나 상태/규칙 일부가 불명확함 | 데모 구현 가능, 운영 전 확인 필요 |
| 참고 | UX/UI 참고 화면으로 보이나 서비스 본류 여부 불명확 | 개발 대상에서 보류 |
| 누락 | 메뉴명만 있고 기능 규칙 없음 | 기능정의 필요 |

이 구분 없이 전부 개발 대상으로 보면 범위가 흔들린다.

## 5. 출제자 기능을 개발하려면 추가로 정해야 할 것

현재 출제자 영역에서 특히 필요한 결정 사항은 다음과 같다.

### 5.1 시험 출제하기

| 항목 | 결정 필요 |
|---|---|
| 출제 대상 | 출제자가 직접 시험을 고르는지, 관리자가 배정하는지 |
| 문항 유형 | 객관식, 주관식, 단답형, 프롬프트, 번역 중 무엇을 지원할지 |
| 입력 필드 | 문제, 보기, 정답, 모범답안, 해설, 채점기준, 배점 |
| 저장 방식 | 임시저장, 제출, 자동저장 여부 |
| 제출 후 처리 | 수정 가능 여부, 반려/승인 흐름 |

### 5.2 출제 내역

| 항목 | 결정 필요 |
|---|---|
| 목록 기준 | 내가 작성한 문항 기준인지, 시험 회차 기준인지 |
| 상태값 | 임시저장, 제출, 검토중, 반려, 승인, 게시완료 |
| 가능한 작업 | 이어쓰기, 수정, 삭제, 재제출, 복사 |
| 반려 처리 | 반려 사유, 수정 이력, 재검토 요청 |

### 5.3 전문가 프로필

| 항목 | 결정 필요 |
|---|---|
| 기본정보 | 이름, 연락처, 이메일, 소속 |
| 전문 분야 | 시험 분류와 연결할지, 복수 선택 가능한지 |
| 경력/학력 | 증빙 파일 필요 여부 |
| 정산 정보 | 계좌, 세금 정보, 관리자 승인 여부 |
| 공개 여부 | 관리자 전용인지, 수험생/기업에도 노출되는지 |

## 6. 결론

PDF만으로 기능정의가 누락되는 것은 분석을 잘못해서라기보다 자료의 성격상 자연스럽게 발생하는 문제다.  
PDF는 화면 구조와 UI 힌트를 주지만, 실제 개발에 필요한 상태, 권한, 예외, 데이터 구조, 승인 절차까지 완전히 제공하지 않는다. 또한 원본 Figma의 레이어, 프레임, 컴포넌트, prototype 흐름이 기능 단위로 정리되어 있지 않으면 PDF 분석에서 누락이 더 커진다.

따라서 앞으로는 다음 순서로 진행하는 것이 안전하다.

1. PDF/Figma에서 사이트맵과 화면 후보를 추출한다.
2. 각 화면을 `확정`, `추정`, `참고`, `누락`으로 분류한다.
3. 역할별 업무 흐름을 먼저 확정한다.
4. 원본 Figma의 프레임, 레이어, 상태 화면, prototype 연결을 기능 단위로 재정리한다.
5. 화면별 성공/실패 케이스와 상태값을 정의한다.
6. 그 다음 개발한다.

이 방식으로 가면 PDF 기반 분석의 장점은 살리면서, 개발 중 기능 누락과 범위 혼선을 줄일 수 있다.
